## B03-P0-01 计费模型标识的来源 · 方案 A 已确认（2026-10-10）

| 方案 | 模型标识数据来源 | 计价可信度和代价 |
| --- | --- | --- |
| **A（用户已确认）** | **调用侧每次 Run 明确上报当次实际 `provider` + `model_id`**（可包含供应商返回的具体模型版本，不由 Agent 展示版本或 A07 平台编码推断） | 计价来源最直接；仅当单 Run 能明确唯一计费模型、使用量完整、价格卡匹配时估算。严格 v1 原协议不允许直接插入新字段，须另评审兼容扩展方式 |
| **B** | Agent 登记中维护一个默认供应商/模型，每次 Run **沿用默认值** | 接入最少，但历史 Run 会被模型切换/路由/灰度错误归类；**若不能核对当次真实计费模型，不得仅凭默认值生成可信费用** |
| **C** | 调用侧优先上报当次模型；缺失时登记默认值仅作为“推测模型”辅助展示 | 兼容性较高；必须记录实际来源/推测标志，**推测值不自动参与有依据的估算金额**；需额外的数据质量规则 |

## B03-P0-02 输入/输出 Token 来源、必填和缺失标准 · 已选方案 A（2026-10-10）

**用户已确认方案 A**：从供应商 SDK/API 的实际 Usage（可包括流式响应最终 Usage）获取真实输入/输出 Token；`input_tokens`/`output_tokens` 均为**可选、非负整数**，调用方没取得实际值就保持字段缺失/未知，**不得补 0，也不得用字符数或推测值冒充真实 Token**；缺失不能拒收整条 Run，应保留其状态、时间和耗时。缺少准确计价所需的 Usage 时，**本次成本不可计算**，而不是 0 元。终态单次上报合法；这也与现有 v1 可选 Token 约束兼容。

| 维度 | 已确认的来源/缺失原则与其余未确认细节 |
| --- | --- |
| **展示** | Run 详情显示「输入 Token」「输出 Token」的实际数值或「未上报/不可得」；是否首页/监控/列表展示、格式、单位、具体空值文案待确认 |
| **计算** | 原则上读取实际模型返回的 Usage，单次 Run 的 Token 与其他 Run 不重复。若 Run 内有多次同价模型调用，可在证明**用量不重叠且计费规则可相加**时汇总；输出 Token 中如已含推理 Token 则不二次累加 |
| **来源** | Agent 调用侧包装器、SDK / API 返回的原始计量，或流式最终 Usage 事件。仅字符数、Prompt 长度、Tokenizer 推算不是已核验计费 Token |
| **标准** | 应区分字段**未上报**与供应商真实返回的数字 **0**；不得补零或假定失败不耗 Token。负数无效；是否强制、来源质量标签、缓存读写包含关系、缺省/迟到补报/流式完成、错误/取消/部分覆盖等继续待确认 |

**方案 A（用户已确认：仅收真实 Usage，两字段可选）**：调用侧尽可能从供应商 SDK/API 的实际 usage（含流式最终计量）提取 `input_tokens`、`output_tokens` 并上报，两个字段保持**可选、非负整数**；源平台未返回时缺失/空值，不依据 Prompt 文本估算，也不强制因缺失拒绝整条技术 Run。只有提供了实际 **0** 才存 0；缺失任何计价所需的用量则本次费用标「不可计算」，仍保留状态/耗时。**兼容现有 v1 允许终态独立上报**。

**方案 B（P0 新接入客户端必须提供完整实际 Usage）**：新扩展协议的终态 Run 必须带输入、输出两项真实计量，缺任一项需要专门的缺失状态/拒绝策略（细节待议）；旧版 v1 客户端仍合法但没有成本保障。数据覆盖更高但部分供应商故障/取消/流式中断本来就拿不到 Usage，不能伪造 0 补齐。

**方案 C（真实 Usage 优先，允许单独上报估算 Token）**：若源平台未给实际 Usage，调用侧可基于受控估算方式提供“估算输入/输出 Token”，与真实计量分字段或加质量标签；只作为**估算 Token**，不能混成真实 usage，也不能自动称供应商实际计费量。成本质量/是否允许继续估算须另设标准，数据模型及审计更复杂。

**方案 D**：自定义，例如只要求输入 Token，输出缺失时不计价，或其他业务规则；应明确会导致何种成本覆盖和风险。

**B03-P0-02 已确认记录**：用户选择**方案 A**；真实性、两个可选非负整数、实际无值保持未知/缺失、真实 0 只有供应商实际报告 0 才可写入、缺值仍保留 Run、缺少计价所需 Usage 时费用不可计算，均为本项核心方案。**未批准**：供应商字段映射、流式结束/中断、FAILED/CANCELLED 特殊映射、0 的证据校验、缓存与推理 Token 是否包含总量、迟到补报与更正、样本覆盖率、最大值/异常校验、完整/部分 Usage 质量及新协议版本。**B03-P0-03 已选 B：调用方计算并上报估算金额**；单价来源/维护、价格卡、首页聚合仍待讨论。

## B03-P0-03 单次成本计算责任方 · 已确认方案 B（2026-10-10）

**已获确认前提**：P0 每条 Agent Run 保存实际输入/输出 Token、当次实际计费供应商及模型和本次 `ESTIMATED` 模型费用；B03-P0-02 已确认 Token 可选且只能来自**真实 SDK/API Usage**。当前 v1 的 Run 事件不含金额字段，v1.1 是草案；**不可以直接往严格的 v1 上报 JSON 插入 model/cost 字段**。

| 维度 | 已确认计算责任方与待确认的实施细节 |
| --- | --- |
| **展示** | 单次 Run 的「模型估算费用」及币种、`ESTIMATED` 质量；无法计算时显示未知/不可计算，不能写成真实账单金额，金额格式及 Run 列表/详情位置尚待确认 |
| **计算** | 通常按 `input_tokens × input_rate + output_tokens × output_rate`，并除以费率的 Token 计价单位；只有所用模型/版本/缓存类别与单价确实适用才可计算。金额使用十进制定点，不按浮点数求和 |
| **来源** | **当次真实模型、Token 和自行计算的 ESTIMATED 费用金额由调用方上报（方案 B 已确认）**；模型单价在哪里维护、价格版本如何取得与权限仍待确认；后端接收、保存该笔调用方报送的估算额，不负责权威算价 |
| **标准** | 同一个 Run 的重传/终态更新不得把费用重复加总；不能把调用方随意报出的金额当成已出账；真实用量/模型/价格缺失或存在多模型/不同费率歧义时不可准确估算；成本后续修订/价格变更仍需另议 |

**方案 A（历史备选，未选：后端统一计算）**：调用方只报当次 `provider + model_id + input_tokens + output_tokens` 和其他已有 Run 信息；**后端选择正确的价格版本并统一计算和保存本次 `ESTIMATED` 模型费用**。调用方不负责上报最终金额。优点是费率口径统一、历史可追溯，避免每个 Agent 重复维护单价；代价是需要价格卡配置/后端计算服务。**价格具体由谁维护、按哪个时点选费率、币种和数据库/协议细节仍待批准**。

**方案 B（用户已确认：调用方自行计算并上报估算金额）**：各 Agent 调用方根据自己的价格来源与算法计算本次费用，上报 `cost_amount/currency` 等候选字段；看板主要存储并展示该费用，需记录来源与价格依据，**不能直接声称为已出账**。接入速度可能快，但不同调用方费率版本/优惠/缓存公式可能不一致，统一指标质量难控制。

**方案 C（历史备选，未选：后端计价加调用方参考金额）**：后端仍以中央价格卡/真实 Usage 统一计算权威 `ESTIMATED` 值；调用方可另报参考金额，单独存、对账/比对，**绝不能自动混为同一金额**。便于排查偏差，P0 开发和字段成本也较高。

**方案 D（其他）**：自定义权威计价来源或混合口径；须能明确责任端与收费依据。

**B03-P0-03 确认记录（2026-10-10）**：用户选择 **方案 B**：调用方自行匹配所用模型适用单价，根据真实 Usage **计算并随单次 Run 上报 ESTIMATED 费用**；看板后端接收、校验和存储这一来源的金额，不改为后端重算的权威值。ESTIMATED 非已出账；后端校验深度尚未确认。**未确认**：单价来源/维护权限、版本/生效时点、币种/精度、缓存/阶梯、缺价/不全 Usage、迟到修订、字段和协议版本以及成本日聚合。

## B03-P0-04 模型单价与价格版本 · 已确认方案 A（2026-10-10）

**B03-P0-04 用户已确认方案 A（2026-10-10）**：各 Agent 调用方自行维护其使用模型的**有来源、版本化价格快照**，按本次 Run 的适用费率在调用方计算并报送 ESTIMATED 成本。P0 不强制公共价格服务/看板后端定价。需能追溯本次使用的价格版本或快照，但**具体配置字段、维护和审批权限、版本生效时点**仍待确认；不自动批准所有调用方价格一致性或价格自动更新。

| 维度 | 展示、计算、来源、标准（候选，未确认） |
| --- | --- |
| **展示** | Run 可显示单次 ESTIMATED 费用与币种；是否展开当次输入/输出单价、价格版本和计价单位及其位置待议 |
| **计算** | 调用方使用当次实际计费模型、真实输入/输出 Token 与适用费率计算；不同缓存/阶梯、计费模式另立可验证规则；无适用价不能硬算金额 |
| **来源** | 可选本地受控费率配置、集团共享版本化价格卡、可信供应商官方/企业合约价格；**不要从 Agent 技术来源平台或版本猜单价** |
| **标准** | 应留适用模型/供应商、币种、计价单位、费率版本/来源/生效区间等追溯依据；价格变动不应让已记录 Run 隐式重定价；未知价/多模型歧义不可伪装成已核验费用 |

**方案 A（用户已确认：调用方维护版本化价格快照）**：调用方各自维护使用模型的来源可追溯费率配置；当次记录其输入/输出费率、币种、计价单位、来源/版本/有效期的快照或引用，并用之计算后上报金额。无需首期公共价格服务，但多 Agent 独立维护可能不一致，配置格式、管理员/审核和历史更正另议。

**方案 B（历史备选，未选：共享价格卡、调用方计算）**：由独立公共配置/发布机制管理有版本的模型费率，**调用方按当次适用价格版本在调用侧计算并上报金额与费率版本**；看板接收和保存，不将后端重算作为权威值。适合多 Agent 使用一致费率，但需要共享发布/分发机制；价格负责人、权限、载入/更新方式、实施规模另议。

**方案 C（历史备选，未选：自动读取供应商价格）**：调用方在实际计价时获取可验证的官方/合约价格规则并保存本次价格快照，根据适用费率算完后报送。供应商 Usage API 通常不直接提供与商务合约一致的单价，在线价格也可能改变；若无法确认实际适用费率，不可声称费用准确。更新周期、快照与来源合法性另议。

**方案 D（其他）**：用户自定义费率获取、版本化和共享模式。

| **计算** | 候选**上报覆盖率** = 当前筛选环境/`started_at` 日期内，已保存一笔格式有效 ESTIMATED 金额的唯一 Run 数 ÷ 同范围参与统计的唯一技术 Run 数；**未报 ≠ 金额 0**，实际可信零值（若报送）可计为“已上报”但其真实性证明另议；币种未知的 Run 不应被强行归到 CNY/USD 的覆盖率分母，故覆盖率是否仅按环境/日期而非每币种仍待选择 |
| **来源** | Run 唯一键 `(agent_id,source_run_id)`、状态/环境/`started_at` 和首次成功保存的调用方费用；缺失原因为未返回 Usage、尚未计费、价格缺失、延迟上报、字段格式失败等，但**原因字段/分类目前未获批准，不能猜测哪一种** |
| **标准** | 覆盖率是**上报覆盖率不是价格已核验率或财务实际支付覆盖率**。若分母为 0、日期有未结束 RUNNING、某些 Run 属于旧 v1 无成本协议、迟到回填/费用格式异常，如何展示和处理均需明确；是否把金额纳入 KPI 也独立于是否上报 |

**方案 A（推荐：明确区分缺失/真零，展示上报数与覆盖率）**：页面用**费用已上报 Run 数 / 同范围技术 Run 总数**标示费用数据上报覆盖率，且分别列出“未上报费用 Run 数”；未上报不能显示 ¥0；真实明确报送的数值 0 视为**已上报 0**，不能和未上报混同。按所选环境和 `started_at` 统计日的**Run 级覆盖率**，不因没有原始费用币种就把未上报 Run 强行分配到某个币种分组。P0-06 只做格式校验，因此标签只能叫「费用上报覆盖率」，**不能叫「已核实费用覆盖率」**。分母、冲突、无有效 Run、质量/币种缺失的细分规则仍待确认。

**方案 B（精简：仅分缺失/真零并展示上报数量，不展示百分比）**：单次 Run/Agent 详情分别显示有金额/真实零/未上报，并在首页显示已报 Run 数与未报 Run 数，但暂不计算百分比，避免 P0 Run 范围、历史延迟和未知币种造成覆盖率解释困难。是否显示「费用覆盖不足」提示由后续单独确定。

**方案 C（仅各币种金额卡，缺费在明细体现）**：集团首页只展示各环境和币种的已报估算金额，不展示覆盖率、已报/未报数量；在 Run 详情中区分真实零和缺失。UI 最简洁，但部分上报会让管理层误读成当日全部模型消耗，必须另评估警示说明。

**方案 D（其他）**：用户自定义费用上报覆盖率口径、分母或缺费提示层级。不得未经同意将覆盖率当作财务准确率。

**本轮已确认的仅是缺费与真实零的用户可见区分、展示上报数量和 Run 级覆盖率的方向**。费用金额字段的真正必填/Null/零校验、详细状态枚举、供应商 Usage 异常、金额质量与 KPI 汇总准入（P0-06 基础格式 ≠ 真实性校验）、Run 终态是否作为覆盖率分母、旧 v1 无成本字段的样本、RUNNING 的首次费用时点、币种未知时的分组、时间窗口/时区、补报后动态回填与冻结、环境选择、下钻和审计仍待后续具体确认。

**B03-P0-12 确认记录（2026-10-11）**：用户选择**方案 A**。在 Run/Agent 明细中区分正数金额、调用方明确上报的 0 与未上报费用；集团首页在分环境、分币种的「今日模型估算费用」之外，展示**费用已上报 Run 数、未上报 Run 数及费用上报覆盖率**。统计方向是按授权环境及 Run `started_at` 日筛选的**唯一 Run 级**上报情况；真实上报 0 计作已上报，未报金额不作 0，未知币种的未报 Run 不得被假定为 CNY/USD 等单币种分母。标签**只能叫「费用上报覆盖率」**，不得称「费用真实准确率 / 已核验费率率 / 已出账覆盖率」。

## 一、目标与真实性

- **MVP 目标**：能依据模型/供应商真实返回的 Token usage 与**带有效期和版本**的费率卡计算 Agent 的**模型调用估算成本**，再汇总到 Run、Agent、集团。若收到供应商可验证的逐笔计费记录，另存真实已出账费用。
- **成本标签分离**：Token×配置价格 = `ESTIMATED`，不冒充 `BILLED`；未知费用为 `UNAVAILABLE`（null），不能是 0。价格无法匹配、模型未知、Usage 缺失时不生成可信金额。
- **范围限制**：本计算主要覆盖**模型推理 API 费用**；工具/API、联网搜索、向量存储、基础设施、人工复核等可能有**非 Token 费用**，除非另有可靠数据，不并入“模型 Token 估算”。是否扩展为“总成本”需另议。
- **不能把示例价格当厂商现价**：定价可能随模型版本、区域、输入长度、batch/实时、缓存、合同变化。**P0 已确定由各 Agent 调用方自行维护有来源、版本化的费率快照**；具体维护及审批人员仍待确认。不能用后来更新的费率静默覆盖已记录的历史费用。

## 二、仓库现状与准确性缺口

| 事实来源 | 已有能力 | 当前缺口 |
| --- | --- | --- |
| Run v1.0 | 可选 `input_tokens`、`output_tokens`，每次外层 Agent 执行的 `agent_code/run_id` 与幂等键 | **无模型 ID/供应商/缓存命中量/模型调用次数或计价版本**。仅适用于能证明一个 Run 由同一计费模型调用构成的有限场景；不得仅因登记有一个 `Agent version` 就套模型价格 |

| 原型 HTML | 固定 `¥308` / `单均 ¥0.46` 与 `perfData.today × perfData.cost` | 全是演示数据；**不用于生产计价** |

## 三、计价对象与采集分层

**用户已确认的 P0 最小记录粒度 = 一次 Agent Run**；**P1 才建议**将最小采集粒度细分为一次实际模型 API 请求（model_call）。Agent Run 可以调用零次/一次/多次不同模型；完整阶段的层级候选为 `agent -> run -> model_call -> measured_usage -> price_version -> cost_entry`。P0 不要求建设 `model_call` 明细表。

1. **P0 已选：Run 级单模型计价档**：调用方能证明每个 Run 的可计费用量对应一个已知计费模型，且 Run `input_tokens/output_tokens` 是源端真实使用量；在 Run 记录保存模型标识、两类 Token 和该次的成本估算值（并保留价格版本依据）。**不要求从 Run 虚构一个 model_call 记录**；内部调用有不同模型/价格档位时不强行套算，留给 P1。模型无法确定、用量不全、计费可能混合时成本标记 `UNAVAILABLE`。
2. **完整接入档（多模型/缓存/工具调用）**：在 Agent 调用侧 wrapper/Gateway 采集每个实际模型 API 请求的模型 ID、供应商、计费区域、发生时间、真实 usage（可空的细分项）、稳定 `call_id`。可用**独立轻量 model-call 记录接口或未来版本化可选扩展**，不向现有严格 v1 请求暗加字段；两者如何选待批准。
3. **Run 状态与费用独立**：`FAILED`/`CANCELLED` 的 Run 也可能已经花费模型 Token；不因 Run 失败就清零成本。不含任何模型调用的 Run 成本可能为零，**但只有观测完整时才认定真零**。

```json
  "agent_code": "finance-review-agent",
  "run_id": "run-20261010-001",
  "call_id": "model-call-01",
  "provider": "model-studio",
  "model_id": "provider-model-version",
  "billing_region": "cn-beijing",
  "occurred_at": "2026-10-10T14:35:00+08:00",
  "mode": "REALTIME",
  "usage": {
    "input_tokens_total": 12000,
    "input_tokens_cache_read": 2000,
    "input_tokens_cache_write": 0,
    "output_tokens_total": 1700
  }
}
```

**注意**：上例 `cache_read` 包含在 `input_tokens_total` 内，**不是额外相加**。实际供应商缓存 Token / reasoning Token 的包含关系不一，先经供应商 Adapter 转换为**互不重叠的计费分桶**：`input_normal`、`input_cache_read`、`input_cache_write`、`output_billed`，若源响应无法可靠拆分，则只在相应模型价格规则允许时使用无缓存基础公式，否则**标为无法准确估算**。输出 reasoning tokens 如已包含在 output total，禁止再次求和。

## 四、版本化价格结构建议（字段未批准）

**P0 已选各调用方自行维护价格快照，不要求建立集团共享数据库表。** 下列字段可用于**各调用方本地受控价格文件/配置的概念结构**；如果后续需要共享持久化，`dw_model_price_rate` 仅为 P1+ 候选表名，**不是 P0 已批准建表任务**：

| 字段 | 用途 |
| --- | --- |
| `price_version_id` / `source_url` / `confirmed_by` | 追溯价格卡来源/审核人 |
| `provider`, `model_id`, `billing_region` | 选择对应平台、**真实计费模型**与区域 |
| `billing_mode`, `tier_selector` | REALTIME/BATCH、上下文输入区间/特殊计价档位（若适用） |
| `currency`, `per_token_unit` | 计价币种及单位，建议显式记录每 1,000,000 tokens；**不得默认所有供应商币种相同** |
| `input_regular_rate`, `input_cache_read_rate`, `input_cache_write_rate`, `output_rate` | 四种费率分桶；供应商无对应分桶时记录适用性而不是随意置零 |
| `effective_from`, `effective_to`, `revision` | 历史价格有效期和只读版本，不以新配置覆盖旧价 |

对跨多个 price tier 的模型，Adapter 先依据供应商规则选择**单次请求适用的档位**；有的供应商按请求输入规模决定全单价，有的按月量或特殊模式计价，不得统一假定逐段累进。

## 五、公式与质量

单次模型调用费用：

```text
normal_input = input_total - cache_read - cache_write
amount = (normal_input * regular_input_rate
       + cache_read * cache_read_rate
       + cache_write * cache_write_rate
       + output_billed * output_rate) / price_unit
```

以上公式**仅用于价格卡确实采用这四种分桶、且用量定义匹配的模型**；具体平台可能有其他模态/最低消费/缓存存储/工具调用附加费用，要另补计价组件。单次请求/Run 同一币种成本用 **BigDecimal / DECIMAL** 累加，禁止 double/float。中间至少保留足够小数精度，**不要逐条四舍五入到分后才汇总**。

**纯示意演算（以下不是任何厂商实际价格）**：普通输入 10,000 Token × ¥2/百万 + 输出 2,000 Token × ¥8/百万 = **¥0.036**，质量标记 `ESTIMATED`，同时存 `price_version_id`；既不是 ¥0.04 已出账，也不能据此推断总业务成本。

储存建议 `dw_model_call_usage`：`agent_id, run_id, call_id` 联合唯一、供应商/模型/usage 原始核验摘要、规范分桶、usage_source、计价日期；`dw_model_cost_entry`：call_id、price_version_id、CNY/USD 等 currency、计算前与后金额、质量/来源、计算版本、计算时间、覆盖状态。**真实账单对齐必须另记录 BILLED 项**；不能同时把同一调用的估算和账单作为总成本双计。

**无费用 / 全部覆盖 / 部分覆盖**单独标记。缺失模型价格、Token/usage_source 可信度不足或接口报表只有部分模型请求时，视为**部分估算或不可计算**，严禁默认为 0。失败请求也可能消耗 Token，只有供应商实际用量返回才可准确计算；不要用字符长度/本地 Tokenizer 无证明地冒充计费 Token。

## 六、聚合与后补

- **同一 `call_id` 幂等**：`(agent_id,run_id,call_id)` 唯一；外层 Run 状态事件和模型调用级费用不能在两套汇总中分别再加一次。对最终未结束或迟到的调用费用，基于可重算的事实表/水位增量纠正，不使用永不回滚的前端累计计数。
- **日期归属仍待用户选**：可按所属外层 Run `started_at`（和 B01 对齐）、模型实际调用时间或供应商账单入账时间，三者不可偷换；也要确认时区、TEST/PROD、跨日与历史补价。
- **价格修改处理**：历史费用保留原 `price_version_id` 与计算快照，明确修正规则后才生成修订/调整条目，不因后台更新价格卡让已发布报表静默重算。
- **账单覆盖**：有 PROVIDER_BILL 时独立存财务事实，展示 `BILLED` 与 `ESTIMATED` 的关系及覆盖率；即使供应商账单比估算不同，**不能将估算擅自升级为 BILLED**。
- **UI**：B03「模型 Token 估算费用」优先于含糊的「总成本」，显示币种、费用质量、计价依据和覆盖状态；是否和已出账分栏、无数据文案、KPI 位置、单均成本 B04 方案 B、集团月趋势 B08 方案 A 已确认核心方向但所有精度/质量/展示等细则待确认；详情 C08 仍待单独确认。

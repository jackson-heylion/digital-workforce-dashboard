# 05｜实施路线、验收标准与待讨论决策

> 文档状态：**Draft，方案建议**。迭代时间是团队排期的参考区间，非已承诺发布日期。当前仍未取得源系统接入、生产数据与业务审批确认。

## 1. 总体策略

**先连接已有能力，再证明数据可信，最后评价业务价值。**

数字员工看板应被当成“集团数字员工的运营账本”。看板第一天可以没有漂亮的工时趋势，但不应把随机演示数当作运营结果。

## 2. 分阶段里程碑（建议 6–8 周的试点范围，实际视接入条件调整）

| 阶段 | 建议迭代 | 输出物 | 验收门槛 |
| --- | --- | --- | --- |
| S0：口径与授权 | 第 1 周 | 两个场景责任人、业务任务与成功事件定义、指标字典 v1、SSO 数据范围、接入协议 | 业务 Owner、技术和财务/数据 Owner 对任务粒度和统计口径完成审阅 |
| S1：采集与目录 | 第 2–3 周 | 目录/员工详情基础能力；签名事件接收、幂等、Task/Run、源系统回执、最小监控 | 两个试点场景可回放真实任务全链路；不依赖前端模拟；重试不重算 |
| S2：正式看板 MVP | 第 4–5 周 | 首页、员工详情、执行列表、监控与告警处置、OIDC 授权、数据新鲜度 | 首页与详情一致；异常可指派/关闭可追踪；多角色越权测试通过 |
| S3：效能校准 | 第 6 周 | 工时基线版本化、成本对账、趋势报表、数据质量校验 | 指标能还原来源与计算过程；估算与已核验分开 |
| S4：五场景扩展 | 第 7–8 周及以后 | 采购/巡检/排班 Adapter、SLA 与业务回执、规范化案例展示 | 每个新增场景独立通过任务定义和数据对账验收 |

**投入假设（供估算）：** 1 名前端、1 名后端、场景业务开发按需参与，测试/运维/业务 Owner 兼职配合；若基础 IAM、数据库、消息与监控无法复用，需要重新排期。

## 3. 首期为什么选两类场景

- **菜品调整**：典型“自然语言 → 参数校验 → 业务工具调用 → 业务状态变化”，覆盖审批、高影响变更、同步回执与重复事件。
- **智能报销**：典型“文档输入 → 结构化匹配 → 校验 → 人审 → 外部业务提单”，覆盖长流程、回调、人审和复杂成功状态。
- 两个样本可以检验**短/长流程、同步/异步、自动/人工协作**。通过后再扩充采购（内容交付）、巡检（高频批量）、排班（约束求解）三个模式。

## 4. 最小交付清单（MVP）

### P0：没有就不能算上线

- [ ] 企业 SSO 登录与后端数据范围鉴权。
- [ ] 员工登记、业务/技术双归属、Owner、场景类型、核验状态与接入状态。
- [ ] Task/Run/Step 标准事件契约，至少支持开始、结束、人审、业务回执和错误。
- [ ] 事件鉴权、幂等、补发、乱序保护、源系统对账。
- [ ] 统一筛选的首页/详情，展示数据新鲜度、来源与统计口径。
- [ ] 监控查询、失败/超时/失联告警和状态审计。
- [ ] 两个试点场景真实接入；明确所有其他员工“未接入/待核验”。
- [ ] 查询 API 分页、字段脱敏、审计日志和权限测试。

### P1：第二批价值

- [ ] 每场景工时基线版本及抽样记录；显示理论释放产能与真实财务节约的区别。
- [ ] 使用量和成本账本（按模型、工具、人工、基础设施拆分）。
- [ ] 工作流图存储、流程版本与文档权限管理。
- [ ] 采购、门店巡检、稽查排班的数据适配与场景指标。
- [ ] 质量评价（业务抽检、错误归因、交付可用率）、导出与月报。
- [ ] 业务系统工单/告警协同与审批操作跳转。

### P2：规模化后再考虑

- [ ] 自助接入门户与事件 SDK。
- [ ] OLAP/流式计算高并发升级，跨租户数据治理。
- [ ] 部门预算与成本预测、异常自动根因建议。
- [ ] 资产版本管理、灰度上线和场景复用模板。
- [ ] 如有必要，从只读观测演进到经过授权的安全控制操作。

## 5. 必须进行的测试

| 测试 | 可接受的结果 |
| --- | --- |
| 同一业务任务因超时自动重试两次 | 一条 Task，多个 Run；任务与收益只计一次 |
| 超过 24 小时后回调完成/乱序送达 | 原始事实不丢失，任务状态合法，受影响聚合可重算 |
| Agent 报“成功”，实际源业务写入失败 | 业务最终状态失败，不误报为完成 |
| 正常等待财务审核 | 显示“待人工”，不能算完成或失败；审核时长可分离 |
| Kafka/Webhook 停止上报 | 明确 STALE/采集异常；前端不继续增加虚拟数据 |
| 员工迁移部门 | 历史指标按当时归属或明确公布的重算策略处理 |
| 部门 A 访问部门 B 任务明细/导出 | 必须受后端权限拒绝 |
| 业务报告中的工时与成本 | 可以追溯到具体任务、基线版本、usage 与分摊方法 |
| 相同筛选的首页、列表、详情 | Task 总量可核对，不因查询维度出现无法解释的差异 |
| 告警静默/指派/关闭 | 操作人、原因、时间、状态审计完整 |

建议将这些场景整理成自动化集成测试 + 几条业务回放测试集，作为任何员工“已核验上线”的条件。

## 6. 风险与控制

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 内部多个平台的任务口径不同 | 任务量与节省工时被夸大 | Task/Run 分离、场景单位口径签署 |
| 未取得实际业务回执 | “模型说成功”误判业务完成 | 源系统确认事件，缺失时显示待核验 |
| 公开仓库传播内部原型或业务数据 | 合规与信息泄露 | 只公开脱敏方案；私有仓库存接口/流程细节 |
| 把运行状态与生命周期混淆 | 管理层错误理解上线规模 | 生命周期、接入验证、近期心跳分离 |
| 未校准基线就计算 ROI | 不可审计的夸大收益 | 样本与签署留档，释放产能与现金节约分离 |
| 为“统一”强行重构已有 Agent | 集成周期过长 | 优先采集事件/回执；按场景适配 |
| 看板故障阻断业务系统 | 生产事故 | 业务与采集解耦，发送端缓存/可重试 |

## 7. 待讨论/签署的关键决策（建议默认值）

| ID | 决策题 | 推荐默认 | 需确认的责任方 |
| --- | --- | --- | --- |
| D1 | 平台定位是否只是看板？ | **首期资产目录 + 观测 + 治理，不做 Agent 编排** | 项目发起人/信息中心 |
| D2 | “真实在用”怎样认定？ | 业务负责人签认 + 源事件回执 + 接入在线核验；9/5 仅原型示例 | 各部门业务 Owner |
| D3 | 五个场景按什么单位计“执行”？ | 业务任务 Task；Run/工具调用单独度量；每场景定义完成结果 | 产品 + 场景 Owner |
| D4 | 最重要的展示指标是什么？ | 业务完成/成功、人工介入、成本、**核验后**工时，其他为辅助 | 管理层/财务 |
| D5 | 首期采集路径怎么选？ | 支持 HTTP 事件上报；已有系统可异步 Kafka/Adapter 转换 | 各系统研发 |
| D6 | 用户/组织权限从哪里来？ | 集团 IAM/OIDC + 部门数据范围，业务系统审批独立 | 安全/IAM/业务 |
| D7 | 成本与工时能否列集团 KPI？ | 先标估算，经过采集和基线签署再升级“已核验” | 财务/数据 Owner |
| D8 | 仓库公开是否符合内部资料分级？ | 公开仓库仅保留通用设计；原型、接口和真实数据另置私有环境 | 项目发起人/信息安全 |
| D9 | 监控中心是否允许业务重试/操作？ | MVP 只支持告警处置与原系统跳转，不替代审批 | 运维/业务 Owner |

每个决策记录：`Decision ID / Owner / Date / Options / Decision / Evidence / Impact`，未明确批准前维持“建议默认”，不要用“已定稿”包装。

## 8. 下一次讨论建议先定三项

1. **平台的受众**：先给集团管理层汇报，还是给信息中心开发运维使用？二者决定首屏重点和权限。
2. **试点数据入口**：菜品调整和智能报销能否按 `source_task_id` 提供业务结果回调？若不能，第一阶段需接只读同步适配器。
3. **效能真值**：能否由财务/业务 Owner 为每一类任务签署“人工基线 + 实际复核耗时”的测量方法？否则首版只给工作量与成本，工时必须标明估算。

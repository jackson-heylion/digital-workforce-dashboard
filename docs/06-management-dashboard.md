# 06｜管理层优先：页面信息架构与指标优先级（v1 讨论基线）

> **历史方案，已退出 2026-10-10 确认的 MVP 范围。** 用户明确要求系统只做**Agent 登记、Agent Run 日志采集、看板展示**；本文关于业务 Task/Outcome、Connector 管理、审批/能力绑定、财务工时/ROI、五场景源业务对账或管理层 KPI 重排的建议**均不可当成本期开发需求或验收项**。请以 [17 最新 MVP 规格](17-agent-log-dashboard-mvp.md) 为准；原始 HTML 的 UI-F0 视觉复刻仍保持。


> **已确认决策（来自项目发起人）**：首期受众为**集团管理层优先**（2026-10-09）；同时**首轮页面必须直接还原上传的 HTML 原型**（2026-10-10）。原始页面结构以 [prototype/index.html](../prototype/index.html) 为唯一视觉基准，见 [08 UI 还原验收规范](08-ui-reproduction.md)。**下文首屏重排是 UI-F2 候选方案，不作为 UI-F0 必须实现的布局。**
>
> **未确认内容**：以下首页布局、KPI 排序、默认周期、展现形式、验收阈值，均为设计建议；不等于集团产品委员会/业务部门/财务正式批准的需求。
>
> **来源与边界**：原型 v6 提供“总览 · 数字员工 · 效能”与“监控中心”两项一级导航；主页有 9 名员工（其中原型标记真实在用 5 名）、当日执行/成本/成功率、动态日志及节省工时、成本和场景排行图，另有员工详情与五个场景演示。原型关键数值为演示数据。以下将其改造成面向管理层的结构，不把模拟数据带入正式报表。

## 1. 产品定位与衡量成功的方式

**一句话定位**：集团数字员工经营成果与价值治理驾驶舱，帮助领导看清**建设覆盖、业务交付、效率价值、投入成本、质量风险**。

五个管理决策问题：
1. 已经落地到哪些部门与业务场景？上线是经过验证的吗？
2. 产生了哪些可查证的业务交付，而不是调用了多少次大模型？
3. 相比人工处理，释放了多少有依据的工时？是否仍存在人工复核？
4. 运行花了多少钱？每类工作值不值得继续投入？
5. 哪些场景值得推广？哪些场景需要治理或暂停？

产品成功的判断不是“大屏好看”，而是：管理层可以从任意汇总指标**穿透到员工、任务、证据和口径**；对于无数据的指标不会误以为是 0 或被演示数字误导。

## 2. 信息架构：保留两个一级入口，但更换展示重点

```text
数字员工看板
├─ 运营驾驶舱（原“总览 · 数字员工 · 效能”，默认打开，管理层优先）
│  ├─ KPI：已核验上线、业务交付、经核验释放工时、运行总成本
│  ├─ 业务成果趋势：工时/任务/成本按周期切换
│  ├─ 部门与场景贡献：覆盖、贡献与成本，按相同口径筛选
│  ├─ 数字员工目录：按部门分组 → 员工概览/绩效 → 标杆场景
│  └─ 风险与数据质量摘要：业务成功率、待办、上报完整性
└─ 监控中心（原导航保留，默认不占首屏视觉重心）
   ├─ 异常与责任人（面向部门负责人的摘要）
   └─ 执行流水 / Trace / 技术细节（运维角色下钻）
```

- 原型五个业务案例继续以**员工详情中的场景案例入口**访问；管理层首页可提供“标杆案例”快捷入口。
- 不做首页全量实时日志瀑布流；技术流转移监控中心，首页仅显示重大异常摘要及统计更新时间。
- 默认打开运营驾驶舱；集团高管账号可见集团授权汇总；部门负责人按授权范围下钻；运维仍能打开监控中心。
- 整个 MVP 优先做内部 Web 管理驾驶舱；大屏轮播/TV 模式不是 P0。

## 3. 1280px 桌面版管理层优化布局（UI-F2 候选，非首轮复刻基准）

```text
┌───────────────────────────────────────────────────────────────────────────┐
│ 数字员工 · 集团运营驾驶舱                 统计口径说明 / 数据截至 / 导出（P1） │
│ 维度：集团/部门/场景                  时间：本月（默认）/ 上月 / 自定义      │
├───────────────────────────────────────────────────────────────────────────┤
│ 已核验上线员工数 │ 完成业务任务数 │ 已核验释放工时 │ 当期总运行成本           │
│ 实际值/覆盖说明  │ 同比口径提醒   │ 基线版本提示   │ 已结算/估算拆分          │
├─────────────────────────────────────┬─────────────────────────────────────┤
│ 价值/工作量趋势                      │ 部门/场景贡献                      │
│ 工作量/工时/成本切换，按日/周/月       │ 业务贡献 + 覆盖 + 口径标注          │
├─────────────────────────────────────┴─────────────────────────────────────┤
│ 数字员工目录（按业务部门；已上线 / 试点 / 规划 分开）                       │
│ [员工卡] 业务目标、核验状态、已完成任务、业务价值、Owner、下钻链接          │
├───────────────────────────────────────────────────────────────────────────┤
│ 运行质量与可信度：成功率 / 人工介入 / 重大异常 / 已接入场景与数据覆盖       │
└───────────────────────────────────────────────────────────────────────────┘
```

**排序理由**：管理层先看成果与价值，再看“谁贡献的”，最后判断数据是否可信与哪里有风险。技术监控不能反过来占满首页。

### 响应式与交互

- 桌面视口 1280px 建议 12 列网格，四张首要 KPI 并排；平板两列、手机单列。
- 顶栏固定：时间范围、业务归属部门、场景。高级过滤“来源系统/数据可信度”可折叠，不让管理层操作复杂配置。
- 默认时间建议**本月至今（MTD）**；与上月比较必须使用**同样已经过去的日数**并注明日历/营业日口径；历史不足时不显示“上涨 X%”。
- 员工数量统计是**截至查询结束时刻的存量快照**；任务/工时/成本是**时间窗累计流量**，比较规则不同。
- 时间窗变化同步刷新所有图表；查看图表口径可展开“分子/分母/证据/更新时间/覆盖率”。
- 点击集团数 → 部门/场景明细 → 员工绩效 → 业务任务/来源回执；未授权明细不展示。
- 用户刷新后保留筛选器是可选增强，不是首期上线阻塞项。

## 4. KPI 优先级：四张主卡 + 质量副指标

| 优先 | KPI | 管理层看到什么 | 定义与防误导要求 | 来源/成熟度 |
| --- | --- | --- | --- | --- |
| P0 / 主卡① | **已核验上线数字员工** | 集团建设覆盖规模（名）与部门分布 | ACTIVE 且业务 Owner 核验/接入接通；“规划中/接入中/失联”不能混入 | 资产目录 + 核验登记 |
| P0 / 主卡② | **完成业务任务数** | 数字员工交付的业务工作量（件） | 终态任务、按完成日去重；**跨不同任务类型只能说明工作量规模，不是同质生产力** | 源系统业务回执 |
| P0 / 主卡③ | **已核验释放工时** | 相对人工流程可释放的容量（小时） | 仅统计有经业务方核准基线的成功任务；扣除人工处理/复核和新增返工；样本覆盖率必须并列 | 人工基线 + 任务事实 |
| P0 / 主卡④ | **总运行成本** | 本期投入（元）与已结算/估算占比 | 模型/工具/API/人工复核/可归属基础设施；避免同笔成本多次求和；结算缺失需标示 | 费用账本 + 计费/分摊凭证 |
| P0 / 质量副指标 | **业务成功率** | 任务终态的可靠程度 | 分子成功任务/分母成功+失败终态任务；审核中/取消单列；不同场景需下钻 | 业务回执 |
| P0 / 可信副指标 | **数据覆盖和新鲜度** | “这些数字代表了集团多大一部分？” | 已接入场景/已确认总场景；任务上报完整率需有源系统对账凭证 | 接入登记 + 日对账 |
| P1 | **单位工作成本** | 某一类型任务的单位成本 | 只能同一业务单位与任务类型内对比，不用“全集团每次调用平均成本” | 费用账本/场景口径 |
| P1 | **业务一次自动完成率/人工介入率** | 人机协作程度 | 不是成功率；强制人审可能是合规要求，不能一律判低效 | Run、人工协作事件 |
| P1 / 有认证条件 | **收益/ROI/净收益** | 投资价值是否超过投入 | 需要经过财务认可的货币收益归因；“节省工时×平均工资”不自动等于财务收益 | 经认证收益 + 全成本 |

**“已核验释放工时”未具备认证条件时：主卡仍占位为“待核验”，展示可覆盖的任务类型数/待核验状态，绝不默认填 0，也不把估算小时伪装成已核验值。**

**成功率和规模应成对阅读**：新接入少量高难业务会改变全局成功率，不能仅因全集团比率下跌就断言系统质量恶化；列表应同时展示场景成功率及任务量。

## 5. 首页区块设计与空数据行为

### 5.1 业务价值趋势（P0）

图表默认可切“完成任务数 / 已核验工时 / 总成本”；首期可展示日级或周级趋势。有可核验数据的月份不足时显示“数据积累中”，不从累计数反推月度曲线。

与上一周期的对比必须注明可比口径；异常突变与统计回补要有脚注。工时/成本的“已验证/估算”不可混为同一根柱。

### 5.2 部门和场景贡献（P0）

管理层想知道“在哪些部门推广有价值”。建议先展示每个部门的：
- 已验证上线员工数、已交付任务、已核验释放工时、成本、已接入覆盖；
- 典型场景标签及业务 Owner 归属。

**不同场景任务体量不一**：巡检一次计划、排班一个周期、提单一份账单，不能仅按任务数直排成“谁最有效率”。贡献排行默认优先工时（若通过核验）、其次覆盖规模、最后交付量；工时缺失的员工展示未评估，不强行排名。

### 5.3 员工目录（P0）

按**业务归属部门**分组（建设部门另显示）；支持名称/场景查询，默认已核验上线在前，试点/规划明确分组。
每张卡用管理语言写：
- 主要工作：比如自动汇总并提交费用提单；
- 业务部门/Owner（公开设计里只保留角色，不提交实际姓名）；
- 生命周期与**接入可信度**双状态；
- 交付量、业务价值（缺数据时为“待核验”）、最近可用数据时间；
- “查看绩效”“查看场景流程”入口。

### 5.4 风险与可信度摘要（P0）

只展示影响业务交付的**重大异常**、待人工处理事项以及数据覆盖/延迟；点击再进入监控中心。普通 API 重试、单次 Token、技术日志不占经营首页。

## 6. 二级页：一个管理故事，而不是技术日志

### 6.1 员工绩效卡（P0）

推荐顺序：
1. 员工职责：服务哪个部门、解决什么人工问题、接入状况与责任人；
2. 本期成果：交付任务、业务成功率、已核验工时、成本及可信度；
3. 前后对比：原人工流程步骤/时长与数字员工当前流程；
4. 趋势：同一场景内成本、工时、业务成功率；
5. 场景案例与流程图：输入→处理→人审→业务回执；失败/风险摘要；
6. 证据下钻：业务任务流水、任务回执、完整 Trace（运维权限）。

### 6.2 标杆场景（P0）

沿用原型五个场景：智能报销、菜品调整、采购情报、门店巡检、稽查排班。每个案例以“三句话 + 一个流程 + 3 个数字”为主：
- 过去如何工作；
- 现在数字员工如何处理、哪些地方要人确认；
- 成果是什么、采集证据是什么、哪些指标仍待核验。

**不得把“原型自述真实在用”自动写成“已验证生产接入”。** 正式页面须展示业务 Owner 的验证与数据证据。

## 7. 展示状态与报告安全

指标展示有四种独立状态：
1. **已核验**：业务来源和口径已验证；财务价值另需财务签认。
2. **估算**：已明确样本/公式但尚未完成审核，醒目标注“估算”。
3. **待核验/未接入**：没有计算条件或没有来源。展示“—”，不能当作 0。
4. **数据延迟/异常**：原本有数据，但源系统同步异常，需显示上次成功同步时间。

“真正为 0”的情况单独显示 **0**。原型 DEMO 仅存在独立沙盒/显式演示开关，不能与正式指标混合。

所有财务/人员敏感字段不进入公开 GitHub；下载报表应鉴权、带筛选条件与指标版本。

## 8. 建议验收清单（管理层优先增量改造 UI-F2）

- [ ] 打开首页，30 秒内能识别“建设覆盖、业务交付、工时价值、投入成本”四类信息。
- [ ] 无正式源数据时明确“待接入/待核验”；不会通过浏览器计时器创造执行数。
- [ ] 核验工时为空时显示未核验，不显示假的月度增长。
- [ ] 比较“本月 vs 上月”时使用同期窗口，且注明截止时间。
- [ ] 从首页总数能下钻至业务场景和员工，并查到具体业务任务证据。
- [ ] 场景内任务数与集团汇总严格一致；跨场景的效率排行不会偷换任务单位。
- [ ] 同一用户无权限的部门指标在前端和后端都不可获取。
- [ ] 看板无需与生产业务处理同步可用，源事件断连时显示告警与数据延迟。
- [ ] 只在生产业务事件与核验口径具备的前提下使用“已上线/真实效能”等措辞。

## 9. 暂不确定，需进一步讨论的 UI 选择

- 首页 KPI 是否固定四张：推荐四张，成功率及数据覆盖作为质量栏；也可四张+业务成功率第五张。
- 是否需要“管理层汇报模式/全屏轮播”：建议到 P1，避免早期花精力做视觉动画。
- 重要部门是否有单独“部门驾驶舱”页面：推荐 MVP 先通过过滤条件实现，确认使用频率后再独立建页。
- 工时基线能否在首期取得足够覆盖：若不能，考虑把“已覆盖场景数”提至第三卡，但**不改变指标口径名称和真实性标签**。

# 01｜附件原型 v6 审阅与设计诊断

> 来源：用户提供的《数字员工看板_可交互原型.html》，页脚标注“v6 / 2026-09-23”。本文件将**原型可观察内容**与**本项目建议**分开叙述。原型的“真实在用/已建成/决策已定稿”等表述**尚未经生产系统或相关部门核验**。

## 1. 原型包含什么（观察）

**一级导航只有两个：**
1. `总览 · 数字员工 · 效能`：总员工数、当日执行数、当日成本、成功率；实时动态；按部门员工卡；月度节省工时、成本趋势与场景排行。
2. `监控中心`：当日执行、成功率、人工介入、异常；实时告警“处理/忽略”；最近执行流水。

**由总览进入两个二级页：**
- 员工详情：累计执行、一次通过率、工时、今日执行、三类趋势、单文件工作流上传、最新日志。
- 五个真实场景演示：智能报销、菜品调整、采购情报、门店巡检、稽查排班；包括业务流程、外部系统、部分人审和权限规则。

**原型样本：** 9 名数字员工，5 名标为“真实在用”；其余样例仍显示“运行中”。员工卡还展示版本、创建日期、部门、负责人、来源和“运行与绩效”链接。

**实际实现：** 单文件 HTML/CSS/JS + ECharts CDN；员工与历史指标硬编码在前端；通过 `setInterval(..., 6000)` 及随机值滚动演示“实时”；工作流上传通过浏览器 `URL.createObjectURL` 本地预览；告警处理只更改页面状态并弹演示提示；没有可见后端 API、身份认证、数据库持久化或真实业务系统接入。

## 2. 值得保留的设计

- 以**管理层能理解的业务价值**为主线：员工目录 → 运行证据 → 效能，避免纯技术监控。
- 两个一级导航简洁，真实场景从员工卡下钻，适合首期呈现。
- 场景展示业务链路与“谁确认/谁负责”，比仅显示 Agent 名称有解释力。
- 把“运行指标”和“效能指标”放在一个员工详情，便于定位效率低是任务复杂还是系统故障。
- 财务、菜品场景已有明确的审批与权限思想，适合抽象为通用治理能力，但不能直接当成公司批准的上线规则。

## 3. 不宜原样生产化的问题

| 优先级 | 原型现象/缺口 | 正式产品的处理建议 |
| --- | --- | --- |
| P0 | 演示任务流每 6 秒自动造数据；“系统运行中”随网页时钟显示 | 以真实事件驱动；显示采集状态、源系统状态和最后上报时间，禁止将模拟数据标成在线 |
| P0 | 9 名员工均显示“运行中”，但仅 5 名被标为真实 | 拆分“生命周期状态”（拟议/接入中/上线/暂停/退役）与“接入验证状态”（未核验/已验证/失联） |
| P0 | 23 次人工介入与 663 次执行对应的介入率不等于原型固定的 1.8%；其他 KPI 也不同源 | 同一筛选条件下全部 KPI 从同一事实表与度量版本计算，提供分子、分母和舍入规则 |
| P0 | 成功率、成本、工时趋势由静态/拆算数构造 | 使用有凭证的完成事件、计费来源和人工基线；不可验证时显示无数据，不造“真实”趋势 |
| P0 | 告警“处理/忽略”仅操作浏览器 UI | 落库并记录处理人、处理时间、原因、状态和外部工单关联；权限控制 |
| P0 | 缺少唯一业务任务、幂等和跨系统关联标识 | 建立 `task_id / run_id / trace_id / source_event_id`，区分一次业务任务、多次执行尝试和多次模型调用 |
| P0 | 无登录、角色、部门数据隔离与审计功能 | 接集团 IAM/OIDC；管理层/部门/运维/审计 RBAC + 数据范围授权 |
| P1 | 工作流“上传”仅保存在浏览器对象 URL，刷新即失效；切换员工无法持久保留归属 | 真实对象存储、类型大小限制、鉴权下载、版本号、员工关联、敏感文件检查 |
| P1 | 员工详情的 1–9 月趋势按固定权重拆累计值，无实际时间维度 | 后端按事件时间与指定时区聚合；零值与无数据有不同显示 |
| P1 | 采购报告、门店巡检、排班与报销等“任务”的粒度显著不同 | 每个场景定义业务任务完成条件与单次价值基线，再做可比较的总量分析 |
| P1 | 同样昵称“小营”被用于菜品调整与运营日报 | 以全局唯一 `employee_id` 标识；昵称仅用于展示 |
| P1 | 原型按部门展示不等于真实归属：门店巡检在员工目录属信息中心，在场景页属运营域 | 区分建设部门、业务归属部门、负责人及使用部门 |
| P1 | 显示“真实在用/决策已定稿”，但附件无法提供审批证据 | 添加来源证据与签署状态；若未经核验统一标为“原型声称/待确认” |
| P2 | 样例页面与数据强耦合、静态 HTML 字符串插入、缺分页筛选、移动端表格拥挤 | 组件化前端 + API 契约 + 权限控制 + 安全转义 + 可访问性与响应式优化 |

**口径附注：**“当日执行任务”与“工具调用次数”、自动成功与人工审核后成功、节省工时与实际可减少工时，都必须分清，避免“指标看起来漂亮但无法审计”。

## 4. 建议页面改造

```text
数字员工运营看板
├── 运营总览（一级）
│   ├── KPI：已核验上线数 / 业务任务完成数 / 业务成功率 / 实际成本 / 已核验节省工时
│   ├── 异常与待人工接管摘要
│   ├── 部门/场景筛选与员工卡
│   ├── 时间趋势和排行（只使用真实来源）
│   └── 员工详情（二级）：SLA、业务任务、步骤/trace、成本明细、业务流程文档与历史版本
├── 监控中心（一级）
│   ├── 告警队列：按严重度、责任人、状态筛选
│   ├── 执行流水：按 task_id / run_id / 源系统追踪
│   └── 处置记录：确认、指派、工单、复核关闭
└── 场景案例（二级，从员工页进入）
    ├── 五类标准业务流程模板与接入状态
    └── 业务输入→处理→人工节点→业务结果→可追溯证据
```

维持原型“**两个一级入口**”，暂不因后台建设增加太多一级菜单。治理配置可以先由管理员入口进入，阶段二再拆“资产治理”。

## 5. 立即需要统一的概念

- **数字员工（Employee）**：可被部门认领且有业务目标、责任人、可重复执行任务的数字能力单元；可能由 Agent、Skill、RPA、规则引擎组合实现。
- **业务任务（Task）**：可被业务方识别的一次“工作委托/处理对象”，是工作量与效能统计基本单位。
- **执行尝试（Run）**：任务的一次自动执行；可失败重试，多次 Run 不能叠加为多个业务任务。
- **步骤（Step）**：模型轮次、工具调用、规则判断、外部 API、人工审批等行为，服务于诊断。
- **人工介入（Intervention）**：因流程要求、置信度/异常或控制策略需要人处理的节点；和失败不是同义词。
- **业务结果（Outcome）**：提单提交成功、菜品实际生效、报告交付成功、告警整改闭环、排班正式发布等，应有原系统回执。
- **效能证据（Baseline）**：任务对应的人工作业时间、可自动化比例、抽样方式与版本；不能拿原型累计数直接当真实节省工时。

## 6. 公开仓库与内容边界

目标 GitHub 仓库为公开仓库。附件原型涉及业务审批策略、对接系统与业务内部细节，**本次未提交原始 HTML**；此文档只沉淀评审结论与可公开的抽象实现方向。真实接口、敏感合同/单据与各部门批准的阈值应存放在私有文档/配置系统。

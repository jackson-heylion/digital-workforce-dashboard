## 第二轮：真实在用数（A02）· 已确认认定方式，细节待议

**原型事实**：首页“真实在用 5”，员工卡 5 人显示“真实在用”，来源为 Demo JS 的 `real:true`；九名员工的 `stat` 均写“运行中”。两者并不等价。实际数据必须独立采集或标记，不能以“最近有 Run”直接推定“正式投产”。

| 维度 | 具体候选定义（尚未确认） |
| --- | --- |
| **展示** | 首页 A01 下方显示“真实在用 X 名”；Agent 卡显示“真实在用”标记；可在详情里显示「使用状态」与「最近执行时间」两个不同字段 |
| **计算** | 推荐 `COUNT(未归档且 operational_status=IN_USE 的 Agent)`；按 A01 相同授权/组织口径，X≤数字员工总数 |
| **来源** | **Agent 登记**中的使用状态字段由负责人员更新；Run 最近活动仅作为辅助展示，不作为“真实在用”认定依据 |
| **标准** | 使用状态必须与“已登记/已启用/近期执行/技术运行中”分开；低频 Agent 无近期日志也可能仍正式在用；无明确状态不能自动判作在用；Test/Demo/停用归属等细则仍待确认 |

**方案 C（双重条件）**：登记标记正式投入使用，且近 30 天有生产 Run；更强调近期活跃，但不能准确表示所有已投产低频 Agent。

**方案 D（其他）**：作为历史备选保留。用户已明确选择 **A**，**不是** B（30天有 Run 自动认定）或 C（必须同时近期活跃）。Test/Prod、暂停/停用在用计数、何人能修改状态、是否审核仍待讨论。

**原型事实**：总览九张员工卡按 `信息中心/财务中心/采购中心/内审部/运营中心` 五组排序，每组显示人数。原型 `emps[].group` 是单个静态字符串，且 `dept` 另含更具体的描述。**原型不能证明生产组织归属一定是单部门，也不能证明部门数据来自 IAM。**

| 维度 | 讨论中的候选方案（尚未确认） |
| --- | --- |
| **展示** | 总览按部门分组，每组显示「部门名称 · N 名」；没有部门的 Agent 是否显示「未分配」需确认 |
| **计算** | 候选 `COUNT(未归档 Agent)`，按登记的归属部门聚合；是否展示子部门与总集团人数对账需确认 |
| **来源** | Agent 登记中的 `department_id` + 部门名称；部门手工维护或复用现有组织目录需确认 |

- **B（按使用部门多归属）**：一个 Agent 可以归属/服务多个部门，出现在多个组里；各部门合计可能大于集团 A01，需要单独去重。

## 第四轮：员工卡运行状态（A04）· 已确认状态分层，细节待议

**原型事实**：`prototype/index.html` 的 9 张员工卡均被写死为 `stat:'运行中'`；其中只有 5 名 `real:true`。该「运行中」既不是 Agent 技术心跳，也没有依赖真实正在执行的 Run。原型仅是 Demo，不得直接将这个状态作为生产事实。

| 维度 | 待确认候选方案 |
| --- | --- |
| **展示** | 员工卡标题旁保留状态标签（原型布局不变）；可另外展示「最近执行时间」与「正式在用」标记，避免一个状态承载多个含义 |
| **计算** | 登记状态、正式使用认定（A02）、技术执行状态分别定义；当前 Run 是否处于 RUNNING 只有调用方确实上报开始和终态时才可推导 |
| **来源** | Agent 登记中的启用/暂停/停用等管理字段；可选 `dw_agent_run.status` 和可信采集时间；不是静态原型数据 |
| **标准** | 不得因 `enabled=true`、最近有 Run、A02 已正式投用，就宣称 Agent **现在在线或正在执行**；缺少心跳/开始事件时必须如实显示未知/仅最近活动 |

**方案 A（最简）**：主标签仅显示 Agent 登记管理状态（如启用/暂停/停用），最近执行时间在旁边独立显示。**不承诺在线/正在执行判断**。成本最低。

**方案 B（纯自动执行状态）**：只根据最近 Run 判断员工卡显示「运行中/空闲/异常/离线」。但结束才上报一次的 Agent、定时低频 Agent 和采集故障都可能被错误判断为离线，因此**不建议**。

**方案 C（用户已确认：管理状态＋可观测执行状态分层）**：主标签显示登记管理状态；另在能可靠拿到 RUNNING 开始/终态时显示「执行中」辅助标记，同时显示最近执行时间。**未上报 RUNNING 就显示“未提供执行中状态”，不会声称离线**；超过阈值的 RUNNING 只能标「长时间未更新/待确认」，不得自动记为运行失败。阈值本身仍待单独确认。这样保留原型卡片层次，且不混淆 A02「真实在用」。

**方案 D**：用户自行定义显示与判断规则。

**A04 确认记录**：用户选择 **C**。管理状态为主标签，与 A02「正式在用」标识分离；执行中标签有可靠 RUNNING 才显示；最近执行独立展示。**不因此强制生产者必须发送 RUNNING**（已有 v1 “终态一次上报即可”的选择不变）；若只上报终态，卡片可以没有实时「执行中」状态。管理状态枚举、超时阈值、异常/离线探活、颜色、标签优先级仍「待确认」。

## 第六轮：Agent 版本（A06）· 已确认登记维护当前版本，细节待议

**原型事实**：原始 `prototype/index.html` 的 `emps[].ver` 是静态的版本显示字段：如菜品调整助手 `v1.0`、智能报销助手 `v2.1`、自动对账异常分析 `v1.5`、运营日报生成 `v2.0`。详情页将它拼接成“版本 ${e.ver}”。**它不是时间趋势，也没有记录版本升级记录、模型版本或每条 Run 当时的 Agent 版本。**

| 维度 | A06 拟议展示/计算/来源/标准（均待确认） |
| --- | --- |
| **展示** | 员工卡/详情页显示“版本 vX.Y”（保留原型位置）；没有登记版本时是隐藏、标“未填写”还是默认 `v1.0` 待确认，不能凭空默认是真实版本 |
| **计算** | 版本不是累计指标：展示 Agent 当前登记版本字符串，不根据运行次数、模型名称或最后一个 Run 自动推导。若按版本比较成功率，必须能还原每条 Run 的真实执行版本 |
| **来源** | Agent 登记配置/负责人手工更新，或源平台元数据，或独立发布记录（见方案） |
| **标准** | 稳定 Agent 身份不随版本升级变化，升级不能新增一名数字员工（A01）；Agent 版本与所调用的模型版本、Prompt 版本、上报协议 `schema_version` 必须区分；版本号格式、必填、变更历史、旧 Run 归属、环境差异均待确认 |

**A（用户已确认：登记维护当前版本）**：负责人或管理员在 Agent 登记中**人工填写和更新单个当前版本字符串**（如 `v1.0`），员工卡和详情显示此版本；**不会声称过去的 Run 都在当前版本上执行**。不强制改动 Run 上报协议，简单且跨平台可迁移。若以后要按版本对比执行质量，再单独增加快照字段和迁移测试。

**B（自动同步源平台当前版本）**：从百炼、自研 Agent 等平台定期获取版本并更新展示；需要处理平台无版本号、多个环境部署版本不同、SDK 和认证适配，且平台迁移可能断开。

**C（当前登记版本 + 可选 Run 当时版本快照）**：员工卡仍显示负责人维护的当前版本，同时**在执行时可选上报 `agent_version`**，按 Run 保留当时实际版本，用于历史故障和版本发布前后效果对比；跨语言易实现，但需要另评估协议版本兼容、字段校验、数据量与上报覆盖率。**不能擅自把现有 OpenAPI v1.0 或 v1.1 草案当成已包含 agent_version**。

**D（其他）**：按用户定义的版本语义和来源。

**A06 确认记录**：用户选择 **A**。版本由负责人或管理员在 Agent 登记中人工维护**当前值**，不依赖第三方平台同步，不新增逐 Run 快照，也不能把旧执行记录视为“当前版本执行”。命名、必填、默认值、升级历史/回滚、环境差异与校验等仍是**待确认**，不修改现有 Run v1.0/v1.1 草案。

| --- | --- |

**A07 确认记录**：用户选择 **方案 A**；平台编码和业务场景出处说明均为 **Agent 登记时人工维护的两个不同字段**。具体编码选项、两字段是否必填、长度/内容校验、迁移历史、是否记录源平台 ID、卡片与详情的具体布局仍**待确认**，不得把示例 `bailian/self_hosted` 当成已批准枚举，也不修改 Run 上报协议。

## 第八轮：负责人（A08）· 已确认人工登记一个责任主体，细节待议

| 维度 | 候选展示、计算、来源与标准（均待确认） |
| --- | --- |
| **展示** | 复刻卡片底部「负责人：XXX」，详情页可展示联系人或负责团队；是否显示具体姓名、部门或岗位以及无值文案均待确认 |

**A（用户已确认：一个责任主体，登记时人工维护）**：为每个 Agent 维护一个显示型「负责人/负责团队」字段；允许登记人员写姓名、姓名+岗位或团队名，兼容原型格式、成本最低。暂不强制接 IAM/HR；若需要按负责人筛选/授权，未来再增加稳定主体 ID。**提醒：纯文本不能直接用作认证、权限判断或准确的跨 Agent 负责人统计键。**

**A08 确认记录**：用户已选 **方案 A**，登记时人工维护一个展示型「负责人/负责团队」字符串，兼容个人或团队格式，不依赖 IAM/HR 强制同步；不能根据该文字认定用户身份或授予操作权限。字段必填/身份标识/多人共同负责/权限、离职交接/脱敏/历史及按负责人汇总均继续**待确认**。

## 第九轮：创建 / 上线时间（A09）· 已确认系统登记时间，其他细节待议

**原型事实（来自 `prototype/index.html`）**：员工卡底部使用 `emps[].created` 的**静态日期字符串**，显示“创建 YYYY-MM-DD”；例如菜品调整助手 `2026-09-05`、智能报销助手 `2026-08-20`。缺失时 JS 还会回退到演示日期 `2026-08-20`。**原型没有定义“创建”是源平台 Agent 建立日、在看板登记日，还是生产上线日；也不存在可证明的原始上线记录。** 生产不能沿用硬编码回退值。

| 维度 | 候选展示 / 计算 / 来源 / 标准（尚未确认） |
| --- | --- |
| **展示** | 员工卡保持原型日期位置；文字具体叫“创建”“登记”“上线”或分别展示两个时间需要先确认。详情可展示更多，但不能把不同日期标为同一事件 |
| **计算** | 日期不是运行 KPI；直接读取有明确定义的日期/时间字段。创建时点不从首条 Run 自动推断；上线也不等于 A02 人工认定“真实在用”或管理状态“已启用” |
| **来源** | 看板系统写入的登记 `registered_at/created_at`、人工维护的源 Agent 创建日期 `source_created_at`、人工登记的实际首次投用 `launched_at`（任选对应模型，字段名仅候选） |
| **标准** | 时间发生时点与采集/录入时点区分；系统生成字段不可任意改成业务上线日期；时间格式/时区、仅日期或精确到分钟、缺失显示/能否修改/历史校验、已归档和跨环境差异仍待确认 |

**A（用户已确认：系统登记时间）**：看板创建 Agent 登记记录时由**系统自动生成且保留 `created_at`**，卡片显示“登记 YYYY-MM-DD”而非把它误称为实际 Agent 创建/上线；无需外部同步、无需人工提供上线证明。上线时间另议，未来有真实来源再新增独立字段。

**B（沿用原型“创建”：人工维护真实 Agent 创建日期）**：卡片显示“创建 YYYY-MM-DD”，由登记人员**手工填源 Agent 的实际创建日期**；看板本身的登记记录时间仍作为后端审计字段存在但卡片不展示。优点是复刻原型文案、业务语义接近原 Agent 历史，风险是人工日期可能缺失或缺乏来源凭证。

**C（登记与上线分离）**：后台自动记录看板登记时间，负责人另行填**实际首次业务上线日期**；员工卡只显示选定的其中一个、详情页分别显示“登记时间/上线时间”。信息最充分但要定义上线凭证、与 A02 标记的关系及首次上线后暂停/重启/重部署是否改写日期。

**D（其他）**：由用户决定如何区分原 Agent 创建、看板登记及业务上线；可选择其他展示文案。

**A09 确认记录**：用户选择 **A**。系统新建 Agent 记录时自动生成保存 `created_at`，员工卡显示为「登记」，不再用原型的「创建」指代不清的其他事件。**日期格式/时间精度、时区、缺失展示、修改与审计权限、历史导入时间、上线核验、不同环境情况仍待确认**，不将源 Agent 实际创建或上线时间说成已被采集；原始 HTML 不变。

**原型事实**：顶栏有「系统运行中」静态文案和 `#clock` 初始 `--:--:--`。原型指标审计发现脚本未可靠更新该时钟；“系统运行中”**没有实际健康检查**，不能在正式版直接当健康结论。

## 第十二轮（优先核心 KPI）：当日执行任务 / 今日已执行（B01）· 已确认技术 Run 启动日口径，细节待议

**为何跳至 B01**：台账 `A12` 为「目标 ≥95%」的阈值说明，必须先确定 B02 成功率分子/分母再谈阈值目标，因此 A12 保持**待确认**。先讨论首页关键 KPI `B01` 的一次执行如何计数，然后才能讨论 `B02`。

**现有事实**：原型首页写「当日执行任务」；当前已确定 MVP 只追踪 Agent 的**技术 Run** 而非独立业务任务，Run 接入规范 v1 中一个 `run_id` 表示一次实际 Agent 调用尝试；相同 `agent_code+run_id` 的 HTTP 重传幂等，一个真实再次调用 Agent 的重试应产生**新的 run_id**，可统计为新的一次技术执行。调用方只上报终态一次也合法，RUNNING 不必报。`started_at` 全状态必填、终态 `finished_at` 必填。**但 B01 指标是否采纳「按开始时间归日的 Run 次数」仍待用户确认**，不可把已有上报契约等同 B01 KPI 已批准。

| 维度 | 本轮候选展示、计算、来源和标准（均未确认） |
| --- | --- |
| **展示** | 首页 KPI 可以改名「今日 Agent 执行次数」/「今日执行 Run」，按次显示整数；员工卡累计执行/实时动态的显示和联动待另议。避免把单次技术尝试写成「完成任务」。 |
| **计算** | 统计一个自然日内唯一 Agent 技术 Run 的数量，关键待选**开始日** vs **完成日** vs **实际业务任务粒度**；跨日执行、RUNNING 未结束、延迟上报与 HTTP 幂等必须有一致定义 |
| **来源** | `dw_agent_run`，通过调用侧 `POST /api/v1/ingest/agent-runs` 的 `agent_code, run_id, started_at, status, finished_at`（终态）入库，`agent_code` 映射内部 `agent_id`；真实数据质量/缺接入情况另议 |
| **标准** | 一个真实再次调用 Agent 的执行重试与仅 HTTP 上报重传必须区分；技术执行≠业务任务完成；统计时间窗/时区、跨日、迟到入库、取消/失败/RUNNING、测试环境和无数据与真实 0 仍待确认 |

**方案 A（用户已确认：今日启动的唯一技术 Run 数）**：指标改称「今日 Agent 执行次数」，按选定日的 `started_at` 统计 `COUNT(DISTINCT agent_id, source_run_id)`。**真正再次执行 Agent 的重试是新 Run，应计入；同一次 Run 的 RUNNING→终态更新和 HTTP 补报不重复计数**。未结束的 RUNNING 可计为“已启动”，但只在终态才首次上报的 Run 将延迟出现在其开始日，存在补数。无需改动已有 v1 Run 上报协议。

**方案 B（今日结束的技术 Run 数）**：统计选定日 `finished_at` 落在时间窗且已终态的唯一 Run（SUCCEEDED、FAILED、CANCELLED 等具体状态范围待定），指标改称「今日结束执行次数」。不会把尚未完成的执行计入，但跨日长任务被归到结束日；和当日启动量不是同一个概念。

**方案 C（按业务任务计次而非 Run）**：一个业务请求触发多个 Agent Run（重试或多步骤调用），首页**只计一条业务任务**。必须引入可信 `task_id` 或业务请求关联以及业务事件口径，超出当前已确认的“Agent 登记 + Run 日志 + 看板”极简 MVP；只能在另行扩大范围后采用，不能伪装成从 run_id 自然去重。

**方案 D（其他）**：自行定义执行量时间口径与数据来源，需保障可核验。

**B01 确认记录**：用户选择 **方案 A**，明确**按技术 Run 而非业务 Task 计次**、以 `started_at` 归属日期、以 `(agent_id, source_run_id)` 去重；真实 Agent 调用重试有独立 Run ID，HTTP 重传及状态更新复用原 Run ID。**日界时区、跨日具体边界、未结束和取消状态参与、首次终态迟到上报与补数、测试环境、零与数据缺失、文案和展示精度继续待确认**；不能因为本次选择把推荐的边界处理全部默认为已批准。v1 上报协议保持不变。

## 第十三轮：自动化成功率（B02）· 已确认技术 Run 终态成功率，细节待议

**为什么需要单独选**：B01 已批准按启动日计算技术 Run **次数**，但 B02 **成功率** 的分母、时间归属与失败/取消处理尚未确定。成功的**技术 Run** 仅证明调用侧执行成功，不能据此断言业务单据已提交成功、用户请求被正确完成、无人工介入或一次通过。

**现有上报事实**：v1 的 `status` = `RUNNING / SUCCEEDED / FAILED / CANCELLED`，`started_at` 始终必填，终态必填 `finished_at`；同一 Agent 的同一 Run 重报或状态更新不会产生额外样本。终态只报一次也合法。原型卡片另有“**一次通过率**”表述，该项归 C02 单独确认，**不能直接假定与 B02 等同**。

| 维度 | 展示、计算、来源、标准（本轮候选） |
| --- | --- |
| **展示** | 首页「自动化成功率」用百分比；是否改称「技术执行成功率」、小数精度和副标题待确认。**不可称业务成功率、一次通过率** |
| **计算** | 分子、分母、`CANCELLED` 与 `RUNNING` 处理、统计按 `finished_at` 还是 `started_at`、无有效分母时的规则待选择 |
| **来源** | `dw_agent_run` 的可信终态 `status` 和 `finished_at`，或按 `started_at` 的启动队列（视方案而定）；来自同一个 v1 Run 上报/幂等记录 |
| **标准** | 同一 Run 只算一次；技术成功不等于业务成功；避免尚未结束任务导致伪失败率；时区/窗口、迟到上报、按 Agent/集团范围、测试环境、未接入/真实零、成功率与 B01 窗口可比较性继续待确认 |

**A（用户已确认：已明确成功/失败的终态 Run 技术成功率）**：在选定时间窗**按 `finished_at`** 筛选 `SUCCEEDED`、`FAILED` 终态 Run，计算 `100% × SUCCEEDED / (SUCCEEDED + FAILED)`。`RUNNING` 未结束，`CANCELLED` 不进入分母（是否要单独显示取消次数另议）。分母为零不写 100%，建议显示“—/无有效样本”，最终文案待定。**B01 启动日次数与 B02 完结日成功率口径不同，不应直接把 B01 当 B02 分母**。这与现有极简 v1 技术状态最契合，无需引入业务回执。

**B（取消也视作未成功的终态 Run）**：在选定时间窗按 `finished_at` 统计 `SUCCEEDED / (SUCCEEDED + FAILED + CANCELLED)`，取消影响成功率。可以看成“已终止执行中的成功占比”，但主动取消/人为终止并不一定是技术失败；若采用须明确名称。

**C（按启动日的全部 Run 计算当前成功比例）**：在选定启动日按 `started_at` 统计 `SUCCEEDED / 所有已启动 Run`，`RUNNING` 和可能存在的其他终态会临时拉低比例，迟到上报可改变历史数据。可和 B01 采用同一批运行样本，但不是稳定的“已完结技术成功率”。

**D（其他）**：用户自定义状态集合、日期归属或样本质量分层。

**B02 确认记录**：用户选择 **方案 A**，仅 `SUCCEEDED`/`FAILED` 两种已结束技术 Run 在 `finished_at` 对应的统计窗口计算 `SUCCEEDED/(SUCCEEDED+FAILED)`；排除 `RUNNING`/`CANCELLED`，不能替代业务成功率或一次通过率。**时区、时间窗口、显示精度/名称、零分母的展示、迟到补报、环境、数据质量和实际业务成功认定仍待确认**。**A12「目标≥95%」仍待独立决定，既未同意展示阈值也未同意其数值。**

## 第十四轮：成功率目标 ≥95%（A12）· 已确认可配置且无预设，细节待议

**原型事实**：`prototype/index.html` 在首页 KPI「自动化成功率」副标题中写 `人工介入率 1.8% · 目标 ≥95%`（第 192 行），监控中心「执行成功率」下也有 `目标 ≥95%`（第 562 行）。两处数字都只是**静态演示文字**，原型没有对应目标配置表、目标责任人、生效日期、自动判定、告警或考核规则。原型 `96.8%` 也是静态数值，不能倒推目标得到业务批准。

**已确认关联**：B02 方案 A 只确认「按 `finished_at` 对成功/失败技术 Run 计算 SUCCEEDED/(SUCCEEDED+FAILED)」。**目标值是什么、是否应该显示、是统一目标还是分部门/Agent 目标尚无用户决议**。实际业务成功率、一次通过率及人工作业覆盖不在 B02 已确认范围内。

| 维度 | 本轮展示/计算/来源/标准（均属候选） |
| --- | --- |
| **展示** | 在首页 B02 KPI 下方显示「目标 ≥95%」、换成可配置目标、或**不展示目标**；如果保留目标，监控中心同口径是否同步展示及颜色/达标文案待议 |
| **计算** | 「实际技术成功率」仍由 B02 算出，目标本身是**独立管理配置值**，**不是从 Run 自动计算的标准线**。如未来比较“是否达标”，须先决定有效样本门槛、误差/四舍五入和计算窗口；本轮不默认做自动判定或告警 |
| **来源** | 可由产品/业务管理员明确配置的目标表或受控配置文件；不从原型硬编码、Run 日志或所谓行业统一标准取值 |
| **标准** | 目标责任人、生效时间/版本、作用范围（集团/部门/Agent）、数据不足处理、更新审计和授权，及阈值是否用于考核或告警都待确认；单凭 B02 达到 95% 不意味着业务质量达标 |

**方案 A（固定 95% 技术成功率目标，最贴近原型）**：明确把 **95%** 作为当前集团级 B02 **技术执行成功率**的展示目标，首页副标题显示「目标 ≥95%」，监控中心是否同步、配置存储/责任人/生效时间和达标提示另议。**仅作为参考目标文案**，不是行业标准，也不默认触发告警、绩效奖惩或业务通过认定；若用户明确选此方案才可把 95% 视为用户批准的数字。

**方案 B（用户已确认：目标可配置、初始不预置 95%）**：不预设固定成功率目标数值；由授权管理者后续单独维护 B02 的目标。**有已批准且已生效的目标时才显示**，否则隐藏目标行或展示「未设置」（具体空值文案待议）。未来可调整，但首期需决定是后台字段/配置文件（本轮只确认来源方向，具体实现待审）。

**方案 C（取消目标阈值展示，最轻量）**：首页和监控仅展示实际技术执行成功率，不显示「目标 ≥95%」或其他目标提示；不建立目标管理配置。若未来确实要引入管理目标再单独讨论，与已取消的五场景演示不同，此项只是成功率目标展示。

**方案 D（其他）**：按用户提出的目标管理或展示要求定义，例如用分层目标而非集团固定目标。

**A12 确认记录**：用户选择 **方案 B**。目标允许由获授权的管理者在后续维护，**初始没有配置值**；不继承、展示或对比原型固定的 ≥95%，直到有经批准且生效的目标。配置数据存储方式、Owner、范围、有效期、修改权限、达标比较、最低样本、空值文案、告警/考核和首页/监控的一致性全部**待确认**；也没有批准实际完成目标管理功能。**B02 公式不变**。

| **展示** | 首页「当日成本」的实际金额（标币种/数据质量），或区分「已出账/估算」，或数据不可得时移除金额、将位置留给已有真实技术 KPI；原型 `¥308` 严禁用于正式环境 |
| **计算** | 只对**同一币种、同一质量类型且可追溯、无重复**的费用金额汇总；跨币种不直接相加；费用按 Run 开始日、结束日还是账单入账日归属，需选定。**不能**默认「执行次数×硬编码单价」 |

**A（仅展示已出账、可对账的真实费用）**：仅从平台/服务商实际账单或可信已计费记录按相同币种汇总，显示「今日已出账费用」；没有账单数据时显示不可用而非 0。财务真实性相对明确，但 T+1/T+N 出账延迟、账单与每次 Run 的映射、到账日/运行日及覆盖范围仍需单独设计，可能无法实时形成“今日成本”。

**B（已出账 + 有依据的估算分开展示）**：有正式账单时按 `BILLED` 汇总；没有账单但有可信 Token/工具用量及版本化单价时，可**单独**显示 `ESTIMATED` 估算费用，绝不将二者混称「真实成本」。覆盖更广，但需可追溯的计价依据、币种与来源、账单补到时如何替换估算，且 v1.1 草案或外部计费对接尚需另行评审。

**D（其他）**：自行定义成本覆盖范围及数据来源，例如只看模型 API 费用，不混入人工/基础设施，并明确质量。

**2026-10-10 新要求与方案调整**：用户已经明确希望**支持 Token × 模型价格计算**，并追加批准 **P0 每次 Agent Run 先记录输入 Token、输出 Token、实际计费模型标识和该次模型成本价格（计算出的 ESTIMATED 金额，关联版本化单价）**。可行做法是**在调用层采集真实模型 Token 用量，使用带生效时间的模型价格卡统一计价**；输出只能标成 `ESTIMATED`，除非有独立真实账单核验。原 v1 仅有 Run 汇总 input/output_tokens 且无模型标识，**多模型/缓存计费不能直接准确算**。详见 [22 Token 计价方案](22-token-pricing-cost-design.md)。

- **方案 A′：Token 估算费用为主**：使用有据可查的模型 Token usage × 计价卡产生「模型 Token 估算费用」，缺少可靠 usage/价格则显示不可计算；不自动对接真实账单。
- **方案 B′（推荐）：Token 估算 + 真实已出账费用分开**：Token 用量按计价卡生成 `ESTIMATED`，若有可验证账单再独立显示 `BILLED`，同一次调用两者不重复计入实际费用；账单对齐为将来可选扩展，首期不强制对接。
- **方案 C′：Token 能力保留，但当数据不足时先不显示金额**：保留计量与价格管理的设计，运行数据源无可信 usage/模型/费率时不显示静态成本数字，不把未知写 0；不等于放弃 Token 计价能力。

**B03-P0-01 已确认 A（调用方报告真实供应商/模型）；B03-P0-02 已确认 A（只收真实 Token，可选且不补零）**。**P0-03 B、P0-04 A、P0-05 B、P0-06 C、P0-07 B、P0-08 A、P0-09 A、P0-10 C、P0-11 币种分组 A、P0-12 缺失/真零及费用上报覆盖率 A 已确认；B04 已选 B，下一项 B05 人工介入率待讨论；P0-12 分母等细节未定**；币种/日界、缓存/多模型不适用的降级、价格卡维护/审核、估算/账单取舍、额外费用、测试环境、缺失/覆盖率、KPI 布局及 B04/B08/C08 的计算均保持待确认。**不因本次用户要求改动 Run v1/v1.1 OpenAPI 草案、也不默认上线服务**。

## 当前已确认的项目边界（不是指标口径确认）

- 先服务集团管理层；原始 HTML 1:1 还原作为 UI-F0 基准；前端 Vue3/TS/Vite。
- 产品只做登记 Agent、调用处上报 Agent 运行日志、显示看板；不建复杂 Agent 编排/业务回执治理。
- **已确认 A01 方案 A（2026-10-10）**：首页「数字员工总数」统计**未归档已登记 Agent**，包含启用、暂停、停用；归档不计。Agent 的不同部署副本或版本升级不得重复增加总数。该值来源于 Agent 登记记录，而非 Run 活跃情况。
- **已确认 A02 方案 A（2026-10-10）**：真正投入使用由 Agent 负责人或管理员在**Agent 登记信息中主动标记「已正式投入使用」**，「真实在用数」根据该认定状态统计，不以最近 30 天/任意期间有 Run 自动认定，不将登记启用/执行活跃等同「真实在用」。
- **已确认 A03 方案 A（2026-10-10）**：每个登记 Agent 仅有**一个用于统计的主归属部门**；即使由多个部门使用，首页也只归入主部门统计一次，**跨部门使用不重复增加人数**。A03 与 A01 均按相同的未归档范围核对，但没有部门的记录怎么显示仍待确认。
- **已确认 A04 方案 C（2026-10-10）**：员工卡**管理状态作为主状态标签**（启用/暂停/停用仅为待定枚举示意），**正式在用**沿用 A02 单独标识；当调用侧确实上报可信 RUNNING 开始/终态时，另显示**执行中辅助状态**和最近执行时间。没有可靠 RUNNING 观测不得推断正在执行、空闲或离线；长时间未更新亦不得自动改成执行失败。
- **已确认 A05 方案 A（2026-10-10）**：数字员工的**显示名称、职责简介及图标资料由负责人或管理员通过 Agent 登记维护**，不依赖外部 Agent 平台自动同步；注册身份仍以稳定 ID / `agent_code` 区分，不通过重名显示名判断身份。图标用内置选择/文字头像或默认形式属于方案 A 所述方向；具体选型、上传支持与默认规则仍待确认。
- **已确认 A06 方案 A（2026-10-10）**：Agent 当前版本为 Agent 登记资料中的**单个版本字符串，由负责人或管理员人工维护和更新**；卡片及详情仅展示当前登记版本；既不从第三方平台自动同步，也**不增设必需的每次 Run 版本快照**。版本更改不新增数字员工，不能将当前版本追认为过去的 Run 使用版本。
- **仍未确认**：一个复杂数字员工对应多个 Agent 时如何登记/归属；TEST/PROD 或不同来源标识的去重范围；A02 在暂停、停用、归档、测试环境时的计数细则、谁拥有最终修改权限/审核要求、状态枚举与历史；A03 未分配部门、部门来源、组织变动与历史归属、授权范围；A04 管理枚举、RUNNING 是否必须上报、超时/探活、标签优先级；A05 显示名/图标/简介字段长度、必填与展示细节；**A06 版本号命名、是否必填、缺省值、校验长度/格式、升级审计/回滚、测试与生产的差异、旧 Run 版本归属和版本维度质量统计**；A07 来源平台与场景来源；Run 粒度、成功率、成本、工时等。之前工程文档出现的其余公式仍仅为**候选**。

## 第一轮：数字员工总数（A01）· 已确认统计范围

**原型事实**：首页标题“数字员工总数”数字 `9`，取自 JS `emps.length`；副标题“真实在用 5”，取 `real:true` 的人数。原型中九人全部写为“运行中”，其中四人并非“真实在用”。这只是 Demo 数据结构，不能自动推导生产规则。

**历史备选方案（用户已选择 A；以下仅保留决策过程）**：

- **A（倾向推荐）**：数字员工总数 = 所有**未归档**已登记 Agent 数（含暂停/停用）；单独展示“启用数/已接入数”，从资产台账视角完整统计。每个 Agent 的不同部署副本不额外计数，版本升级不新增员工。
- **B**：总数只统计启用 Agent，停用/归档不计入主页总数；可在管理后台查看历史。
- **C**：仅最近一段时间**实际有 Run** 的 Agent 才进入总数；需定义窗口且会把低频或长期计划 Agent 漏掉。
- **D**：其他，由用户定义。

同时要确认概念：**一条 Agent 登记记录对应一名数字员工**是否成立？如果一个业务数字员工背后有多个 Agent，需另行确认关联规则（不预设复杂多对多）。

**确认记录**：用户已在会话明确选 **A**。统计范围和副本/版本不重复的规则已采纳；不会自动将原确认示例中的“一个 Agent 永远等于一名数字员工”“无数据文案”“跨环境去重”视为已批准。下一步讨论 **A02 真实在用数**。

## 第二轮：真实在用数（A02）· 已确认认定方式，细节待议

**原型事实**：首页“真实在用 5”，员工卡 5 人显示“真实在用”，来源为 Demo JS 的 `real:true`；九名员工的 `stat` 均写“运行中”。两者并不等价。实际数据必须独立采集或标记，不能以“最近有 Run”直接推定“正式投产”。

| 维度 | 具体候选定义（尚未确认） |
| --- | --- |
| **展示** | 首页 A01 下方显示“真实在用 X 名”；Agent 卡显示“真实在用”标记；可在详情里显示「使用状态」与「最近执行时间」两个不同字段 |
| **计算** | 推荐 `COUNT(未归档且 operational_status=IN_USE 的 Agent)`；按 A01 相同授权/组织口径，X≤数字员工总数 |
| **来源** | **Agent 登记**中的使用状态字段由负责人员更新；Run 最近活动仅作为辅助展示，不作为“真实在用”认定依据 |
| **标准** | 使用状态必须与“已登记/已启用/近期执行/技术运行中”分开；低频 Agent 无近期日志也可能仍正式在用；无明确状态不能自动判作在用；Test/Demo/停用归属等细则仍待确认 |

**方案 A（用户已确认认定方式）**：由 Agent 负责人或管理员在登记信息中明确标记“已正式投入使用”；启用开关、最近 Run 时间与此状态分开。适用于每日任务与每月任务并存的企业 Agent。候选值 `PLANNED / PILOT / IN_USE / RETIRED` 只是工程建议，尚未获得字段枚举审批。

**方案 B（自动观测）**：例如过去 30 天至少有一次生产 Run，即自动计为真实在用；无需人工维护，但容易误把临时测试算上线，也会漏掉低频 Agent。

**方案 C（双重条件）**：登记标记正式投入使用，且近 30 天有生产 Run；更强调近期活跃，但不能准确表示所有已投产低频 Agent。

**方案 D（其他）**：作为历史备选保留。用户已明确选择 **A**，**不是** B（30天有 Run 自动认定）或 C（必须同时近期活跃）。Test/Prod、暂停/停用在用计数、何人能修改状态、是否审核仍待讨论。

| 维度 | 讨论中的候选方案（尚未确认） |
| --- | --- |
| **展示** | 总览按部门分组，每组显示「部门名称 · N 名」；没有部门的 Agent 是否显示「未分配」需确认 |
| **计算** | 候选 `COUNT(未归档 Agent)`，按登记的归属部门聚合；是否展示子部门与总集团人数对账需确认 |
| **来源** | Agent 登记中的 `department_id` + 部门名称；部门手工维护或复用现有组织目录需确认 |
| **标准** | 唯一稳定部门 ID、不依赖显示名称去重；跨部门共享 Agent 如何计数、部门重组后历史归属、授权范围均待确认 |

- **A（推荐：唯一主归属部门）**：每名 Agent 指定一个负责部门，按主归属分组，集团部门人数相加等于 A01 总人数（包含「未分配」）；其他使用部门不重复计算。
- **B（按使用部门多归属）**：一个 Agent 可以归属/服务多个部门，出现在多个组里；各部门合计可能大于集团 A01，需要单独去重。
- **C（主归属 + 使用部门双维度）**：首页按主归属分组，详情记录多个使用部门，允许按使用部门做独立筛选；灵活但登记与权限较复杂。
- **D**：其他部门归属及统计规则由用户定义。

**A03 确认记录**：用户选择 **A（唯一主归属部门）**。方案 B（各使用部门都重复计数）和 C（首页主部门＋使用部门双维度作为本期要求）均未被选择。组织系统同步、无部门显示、部门改名/撤并及权限仍是「待确认」，不自动加入已确认范围。

## 第四轮：员工卡运行状态（A04）· 已确认状态分层，细节待议

**原型事实**：`prototype/index.html` 的 9 张员工卡均被写死为 `stat:'运行中'`；其中只有 5 名 `real:true`。该「运行中」既不是 Agent 技术心跳，也没有依赖真实正在执行的 Run。原型仅是 Demo，不得直接将这个状态作为生产事实。

| 维度 | 待确认候选方案 |
| --- | --- |
| **展示** | 员工卡标题旁保留状态标签（原型布局不变）；可另外展示「最近执行时间」与「正式在用」标记，避免一个状态承载多个含义 |
| **计算** | 登记状态、正式使用认定（A02）、技术执行状态分别定义；当前 Run 是否处于 RUNNING 只有调用方确实上报开始和终态时才可推导 |
| **来源** | Agent 登记中的启用/暂停/停用等管理字段；可选 `dw_agent_run.status` 和可信采集时间；不是静态原型数据 |
| **标准** | 不得因 `enabled=true`、最近有 Run、A02 已正式投用，就宣称 Agent **现在在线或正在执行**；缺少心跳/开始事件时必须如实显示未知/仅最近活动 |

**方案 A（最简）**：主标签仅显示 Agent 登记管理状态（如启用/暂停/停用），最近执行时间在旁边独立显示。**不承诺在线/正在执行判断**。成本最低。

**方案 B（纯自动执行状态）**：只根据最近 Run 判断员工卡显示「运行中/空闲/异常/离线」。但结束才上报一次的 Agent、定时低频 Agent 和采集故障都可能被错误判断为离线，因此**不建议**。

**方案 C（用户已确认：管理状态＋可观测执行状态分层）**：主标签显示登记管理状态；另在能可靠拿到 RUNNING 开始/终态时显示「执行中」辅助标记，同时显示最近执行时间。**未上报 RUNNING 就显示“未提供执行中状态”，不会声称离线**；超过阈值的 RUNNING 只能标「长时间未更新/待确认」，不得自动记为运行失败。阈值本身仍待单独确认。这样保留原型卡片层次，且不混淆 A02「真实在用」。

**方案 D**：用户自行定义显示与判断规则。

**A04 确认记录**：用户选择 **C**。管理状态为主标签，与 A02「正式在用」标识分离；执行中标签有可靠 RUNNING 才显示；最近执行独立展示。**不因此强制生产者必须发送 RUNNING**（已有 v1 “终态一次上报即可”的选择不变）；若只上报终态，卡片可以没有实时「执行中」状态。管理状态枚举、超时阈值、异常/离线探活、颜色、标签优先级仍「待确认」。

## 第五轮：员工名称、图标、简介（A05）· 已确认登记维护方式，字段细节待议

**原型事实**：9 名员工由 `emps[]` 内置 `name`、`av`（头像文字，如“菜/巡/报”）和 `cls`（卡片样式颜色）生成；卡片次行 `dept` 是**组织/场景描述文本**，不等于独立维护的员工个人简介。原型没有用外部图片或 Agent 平台 API 自动生成头像/简介，因此这些字段的生产来源需要另行决定。

| 字段 / 维度 | 拟展示与校验（候选，未确认） | 候选来源 | 需特别确认 |
| --- | --- | --- | --- |
| **display_name（显示名）** | 卡片标题 + 详情页标题，中文/英文均可，超长省略并支持完整查看 | Agent 登记手工录入，或外部平台同步 | 显示名是否必填、是否允许重名、最大长度、修改后历史日志如何展示 |
| **icon（头像/图标）** | 卡片左侧圆形图标，可使用统一图标或文字首字；无图标时使用默认样式 | 登记配置/系统默认；可选平台头像地址 | 图标从内置库选择还是允许图片上传、外部链接安全/迁移、默认规则 |
| **description（简介）** | 详情页介绍数字员工职责；员工卡可折叠/截断，原型布局不变 | Agent 登记由负责人维护，或通过平台元数据自动获取 | 简介是否必填、敏感信息过滤、字数上限、平台更新是否覆盖用户维护内容 |
| **统一标准** | 显示名只用于展示，**不能作为身份唯一键**；身份仍由稳定 `agent_code`/内部 ID 关联 | Agent 登记与身份映射 | 图标/简介缺省怎么显示、前端 HTML 转义、可访问范围和历史修改追踪 |

**A · 全部登记维护（用户已选 A）**：负责人或管理员手动维护显示名与简介；图标可从内置图标/文字头像选择，缺少时使用默认；**不依赖外部 Agent 平台持续同步**。外部系统的 `agent_code`/源 Agent ID 仅用来保持关联。首期不必开发图片上传与存储。

**B · 全部自动同步外部平台**：登记时从百炼、自研 Agent 等平台同步名称、图标和描述，并随源平台变化刷新；人工修改需要回写源平台或可能被覆盖。平台适配/鉴权/图标地址处理成本更高，迁移后容易变化。

**C · 默认同步 + 人工覆盖**：能从源平台同步则初始化显示名/图标/简介，否则手工登记；允许本地人工覆盖，建立来源/同步冲突规则。灵活，但首期维护复杂度高。

**D · 其他**：用户自定义展示、来源和管理方式。

**A05 确认记录**：用户已选方案 A，名称、图标、简介统一由负责人/管理员在 Agent 登记中人工维护，不做外部平台持续同步。名称是否唯一/必填/限长、图标能否上传及缺省规则、简介字数与卡片布局等**并未因选 A 自动批准**，后续逐项敲定；无需改变 Run 上报字段。

## 第六轮：Agent 版本（A06）· 已确认登记维护当前版本，细节待议

**原型事实**：原始 `prototype/index.html` 的 `emps[].ver` 是静态的版本显示字段：如菜品调整助手 `v1.0`、智能报销助手 `v2.1`、自动对账异常分析 `v1.5`、运营日报生成 `v2.0`。详情页将它拼接成“版本 ${e.ver}”。**它不是时间趋势，也没有记录版本升级记录、模型版本或每条 Run 当时的 Agent 版本。**

| 维度 | A06 拟议展示/计算/来源/标准（均待确认） |
| --- | --- |
| **展示** | 员工卡/详情页显示“版本 vX.Y”（保留原型位置）；没有登记版本时是隐藏、标“未填写”还是默认 `v1.0` 待确认，不能凭空默认是真实版本 |
| **计算** | 版本不是累计指标：展示 Agent 当前登记版本字符串，不根据运行次数、模型名称或最后一个 Run 自动推导。若按版本比较成功率，必须能还原每条 Run 的真实执行版本 |
| **来源** | Agent 登记配置/负责人手工更新，或源平台元数据，或独立发布记录（见方案） |
| **标准** | 稳定 Agent 身份不随版本升级变化，升级不能新增一名数字员工（A01）；Agent 版本与所调用的模型版本、Prompt 版本、上报协议 `schema_version` 必须区分；版本号格式、必填、变更历史、旧 Run 归属、环境差异均待确认 |

**A（用户已确认：登记维护当前版本）**：负责人或管理员在 Agent 登记中**人工填写和更新单个当前版本字符串**（如 `v1.0`），员工卡和详情显示此版本；**不会声称过去的 Run 都在当前版本上执行**。不强制改动 Run 上报协议，简单且跨平台可迁移。若以后要按版本对比执行质量，再单独增加快照字段和迁移测试。

**B（自动同步源平台当前版本）**：从百炼、自研 Agent 等平台定期获取版本并更新展示；需要处理平台无版本号、多个环境部署版本不同、SDK 和认证适配，且平台迁移可能断开。

**C（当前登记版本 + 可选 Run 当时版本快照）**：员工卡仍显示负责人维护的当前版本，同时**在执行时可选上报 `agent_version`**，按 Run 保留当时实际版本，用于历史故障和版本发布前后效果对比；跨语言易实现，但需要另评估协议版本兼容、字段校验、数据量与上报覆盖率。**不能擅自把现有 OpenAPI v1.0 或 v1.1 草案当成已包含 agent_version**。

**D（其他）**：按用户定义的版本语义和来源。

**A06 确认记录**：用户选择 **A**。版本由负责人或管理员在 Agent 登记中人工维护**当前值**，不依赖第三方平台同步，不新增逐 Run 快照，也不能把旧执行记录视为“当前版本执行”。命名、必填、默认值、升级历史/回滚、环境差异与校验等仍是**待确认**，不修改现有 Run v1.0/v1.1 草案。

## 第七轮：来源平台与场景来源（A07）· 当前待确认

**原型事实（直接来自 `prototype/index.html`）**：员工卡下方使用 `emps[].src` 文本展示“来源：…”，例如：
- 菜品调整助手：`研发对接清单·菜品场景`
- 智能报销助手：`研发对接清单·报销场景`
- 门店巡检助手：`门店监控系统对接`
- 采购情报助手：`采购 Agent+Skill（已建成）`
- 运营日报生成：`运营日报（演示）`

这些描述有的是**业务接入/方案出处**，有的是演示标记；**原型没有单独存储百炼/自研等技术平台的结构化 `platform` 字段**，不能将 `src` 字符串等同于 Agent 运行平台、实际数据接入状态或 A10 场景关联。

| 维度 | 待选方案的展示、计算、来源、标准 |
| --- | --- |
| **展示** | 员工卡延续原型“来源：XXXX”的业务出处短文本；详情页可分别显示“技术平台”与“场景/业务来源”两项；是否都在卡片展示、空值文案和详情交互待确认 |
| **计算** | 平台与场景来源均为登记元数据，不需要 Run 指标求和；按平台筛选/分组时应依赖**平台编码**，不是模糊匹配“来源”文字；“业务来源”不自动等同已真实在用 |
| **来源** | `Agent 注册记录`中候选 `platform_code`（如 `bailian`/`self_hosted`/`other`）及 `source_note`（人工维护的对接出处/业务说明）。字段命名和枚举尚未批准；原型 `src` 仅示例 |
| **标准** | 平台与业务来源**分开**、支持环境/供应商迁移（A01 身份不因平台显示更改而增加人数）；A02 正式在用由负责人标记，不根据出处文字判断；A10 的五场景绑定另议；可见范围、字段长度与缺失处理待确认 |

**A（推荐：两项登记资料，人工维护）**：在 Agent 登记时由负责人维护①结构化“技术平台”，②自由文本“业务/场景来源（出处说明）”；员工卡可以保持原型的“来源：说明”，详情额外展示平台。**不建设自动探测/厂商 Connector**；迁移技术平台时更新当前登记信息即可，历史 Run 平台归属是否追踪另议。

**B（技术平台由接入凭证/调用适配层确定，业务来源人工维护）**：在采集凭证或已有 Agent 平台适配信息中可靠绑定/推导技术平台，`source_note` 人工维护。避免人为填错平台，但需要梳理采集凭证与平台映射，且不能将 HTTP Reporter 的实现语言误当 Agent 运行平台。

**C（完全沿用原型单个来源文本）**：只登记和显示一个 `source_note`，如“研发对接清单·菜品场景”，暂不单列技术平台。UI 还原最快，但后续无法按真正的百炼/自研平台准确筛选/迁移，若需要平台分析必须再结构化改造。

**D（其他）**：发起人自行定义，比如只显示平台，不显示业务出处。

**本轮确认 A07 的整体显示字段与信息来源方案**；`platform_code` 的选项/是否必填、`source_note` 长度/敏感信息、是否记录源系统 ID、迁移历史、数据质量/缺失默认、卡片还是详情分别放哪个字段等**仍待确认**。

## 紧随其后的优先确认顺序

1. **A01/A02/A03/A05/A06 方案 A，A04 方案 C 的核心口径已确认** → **A07 来源平台与业务场景来源（当前讨论）**；未明确细节继续待确认；
2. B01 执行次数的 Run 粒度（核心），B02 成功率和时间窗口；
3. B03/B04 费用来源与统计，B05/E02 人工介入与统计完整率；
4. B07/C03 工时节省的人工基线及可信度；
5. B06/E08 实时流水与数据安全；
6. D01-D11 场景统计口径以及 E04-E07 告警语义；
7. A/C 其他展示字段、F/S 协议级校验、展示精度、性能、迁移验收。

**重要**：此顺序是讨论次序，不是已批准的开发优先级。任何指标无法取到有效来源，必须明确显示“未接入/不可计算”，不能在生产沿用原型静态数字。

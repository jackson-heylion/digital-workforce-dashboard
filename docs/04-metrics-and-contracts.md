# 04｜Agent Run 指标与日志契约（极简 MVP）

> **产品口径审批约束（2026-10-10）**：用户要求每个指标和字段的展示、计算、来源与标准都逐项讨论确认。请查阅 [21 · 指标字段待确认台账](21-metrics-field-confirmation-register.md)。本文件中的 KPI 公式只是此前研发建议，**不能视为逐项已获用户确认的产品口径**。

> **Run 上报标准 v1**：[18 人类可读规范](18-agent-run-reporting-standard.md) | [OpenAPI](../openapi/agent-run-reporting-v1.json)。该标准是最新接入契约。
>
> 最新范围以 [17](17-agent-log-dashboard-mvp.md) 为准：**只登记 Agent、采集 Run 日志、展示技术运营指标**。下列字段/公式是建议版本 v0.2；接入时必须按真实平台数据验证。**不再要求源业务最终回执、独立业务 Task、工时与 ROI 核验。**

## 1. 最小实体

- **Agent**：平台中登记的一个外部 Agent 实例；`platform + environment + external_agent_id`（多空间需补 namespace）对应唯一内部 `agent_id`。
- **Run**：这个 Agent 的**一次技术执行**；由源 `run_id` 唯一标识，可能已完成/失败/取消/运行中；没有 Run ID 的源先定义稳定替代键，否则不能可信去重。
- **Log（可选）**：Run 中的时间、级别、脱敏短消息与错误；不能把每条日志记成一次 Run。
- **部门/Owner**：Agent 登记字段，按授权查询；改部门后的历史归属口径先采用“按当前归属”，如果需要历史回溯再补快照，必须展示此限制。

> **A10 取消场景演示（2026-10-10）**：员工卡场景演示入口、五场景静态页面、Agent—场景关联及其专属 D01–D11 演示页计量均不进入新 Vue/正式版本。保留 A07 业务来源说明和一般技术 Run 指标；现有 v1 上报协议无须添加 `scenario_code`。原始 HTML 不修改。

| **顶栏时钟（A11 已确认 A）** | **仅显示当前时间**，移除原型静态「系统运行中」健康结论文案；不计算健康率、在线率或 Run 数据新鲜度 | **浏览器当前时间**，不需后端健康 API、Run 最近记录或服务状态推断 | 时区、格式、刷新频率、时钟异常和未来独立健康监测的状态规则/阈值/告警均待确认；不得虚构系统健康状态 |
| **A12 技术成功率管理目标（方案 B 已确认）** | **允许后续配置目标，但初始无预设目标，不沿用原型 ≥95%**；只有已确认、生效的配置才可展示实际目标数值；缺省布局未确认 | 独立的管理目标配置（具体表/配置文件及维护主体未决）；与 B02 的实际技术成功率计算分离 | Owner/适用范围/生效时间/编辑权限/最低样本/达标规则/告警/绩效和首页监控同步展示均待确认；**可配置不表示已实现目标管理后台** |
| **B01 今日 Agent 技术执行次数（方案 A 已确认）** | **按 `started_at` 归属到启动日**，统计唯一 `(agent_id, source_run_id)` 的技术 Run；真实重新调用产生新 Run 可加次，HTTP 重传及同一 Run 状态更新不得加次；**不是业务 Task 完成量** | `started_at` 启动事件已确认；**日界时区、跨日边界、RUNNING/CANCELLED 纳入范围、迟到补数、测试环境仍待确认** | 实际 Run 来自 `dw_agent_run`；未接入/真实 0 及具体展示文案待确认，**B02 技术成功率尚未批准** |
| Run 执行次数（通用参考，非独立批准 KPI） | 时间窗内 `COUNT(DISTINCT agent_id, source_run_id)` | B01 启动日归属已确认；其他 KPI 单独确认 | 无源接入与已接入真实 0 分开 |
| 已结束 Run 数 | `SUCCEEDED + FAILED + CANCELLED` | finished_at | 无终态为 0 |
| **B02 技术执行成功率（方案 A 已确认）** | **按 `finished_at` 所属统计窗口筛选唯一 Run，`100% × SUCCEEDED/(SUCCEEDED+FAILED)`**；`RUNNING` 与 `CANCELLED` 排除分子分母；同一 Run 的补报/状态更新不重复统计 | **以 `finished_at` 归属日已确认**；窗口长短、统计时区、迟到更新及测试环境过滤仍未确认，**不同于 B01 的 `started_at` 计次** | 零分母的具体展示规则、数据覆盖率与质量、百分比精度/文案待确认。**A12「目标≥95%」未获批准，不能当管理目标或默认告警阈值** |
| 技术成功率（通用工程参考，非额外已批准展示项） | `SUCCEEDED / (SUCCEEDED + FAILED)` | finished_at，同一时间窗 | 零分母工程建议；正式展示另需批准 |
| 技术失败次数 | `COUNT(status=FAILED)` | finished_at | 分母不是成功率计算依据 |
| 平均执行耗时 | `AVG(duration_ms)`，仅有效已完成/失败且有 duration 的 Run | finished_at | 无有效样本 → null |
| Token 消耗（可选） | Sum(input_tokens + output_tokens) | 归属 Run，明确计量来源 | 未提供不显示 |
| **B03 P0 单次 Run Token/模型/估算成本（记录内容已确认，整体 KPI 未定）** | **P0 按一个 Agent Run 保存实际 `input_tokens`、`output_tokens`、模型计费标识及本次模型估算成本**；**P0-01 已确认方案 A：调用方每次 Run 提供当次实际计费模型供应商和模型 ID**，不可从 Agent 登记平台/当前版本推断；**B03-P0-03 方案 B：费用由调用方按照真实 Token × 实际适用的模型费率自行计算并上报，服务端接收存储，不做权威重算**；价格版本依据需可追溯，不采用原型固定每 Run 单价 | v1 已有可选 `input_tokens/output_tokens`；模型 ID、估算费用金额、币种与价格版本等是**待定义协议的候选字段**；用户已批准 P0 记录范围和模型真实来源，但未批准 v1 直接扩字段/字段必填/精度，**P0-02 已确认方案 A：仅真实 SDK/API Usage、两个字段可选、缺失不补零且不拒收 Run、成本不可计算**；P0-03 B、P0-04 A 已确认；**P0-05 已确认方案 B：独立版本的精简 Run 扩展，采用扁平成本/版本依据字段，不复用 v1.1 嵌套 cost 作为 P0 默认结构**；版本号/具体金额字段/必填/精度仍未确认，原 v1/v1.1 草案均不变；**P0-06 已确认 C：费用仅基础格式校验，后端不核验价格真实性/Token 完整性/金额偏差**；**P0-07 已确认 B：相同 Run 允许首次费用晚到补入、首次保存后普通上报锁定金额，后续不同金额只标冲突、不覆盖/累加**；**P0-08 已选 A：B03 一次已存估算费用按对应 Run `started_at` 统计日归属**；**P0-09 已选 A：集团首页主卡「今日模型估算费用」，按实际 Agent 技术 Run 形成 ESTIMATED 模型费用总额方向**；不以当前 A02 正式在用标识删除已发生的历史金额；**P0-10 已选 C：各授权环境分别统计，RUNNING/SUCCEEDED/FAILED/CANCELLED 四状态有已存 ESTIMATED 费用均可在所属环境候选纳入**；**P0-11 已选 A：保留原始计价币种，按环境+`started_at` 统计日+币种分别汇总，不自动换汇或异币种相加**；当前讨论 P0-12 费用缺失/真实零/上报覆盖率，详见 [22](22-token-pricing-cost-design.md) | **实际零只表示被真实测量为零，不等于未上报；跨多模型/不同缓存费率无法套单一 Run 费率时不强行估算**；调用方金额仅作为 `ESTIMATED`，格式通过亦不等于已出账 BILLED 或价格已核准，集团技术 Run 基本范围已选 A；**环境的默认选择、编码/授权、已归档 Agent 历史可见性、币种字段/精度、费用质量和上报覆盖率的纳入仍待确认**；**逻辑归属日已选 `started_at`；晚到费用回填历史日的物理时机/历史报表重算冻结规则仍未批准**；价格表/币种/缺失/展示/日界及 B04/B08/C08 仍待确认 |

**执行次数并非业务任务完成数，技术成功率并非业务成功率**。重复上报同一 Run，不增加执行次数；真实重试生成新的源 Run ID，按新的执行次数计入。

## B05 人工介入率 · 用户已确认方案 B（2026-10-11）

**展示（已确认方向）**：首页和监控展示「已知人工介入 Run 占全部技术 Run 的比例」，并提示部分介入事实未报告可能使比例低估。原型 1.8% 是演示数，不能作为正式值。准确标题/精度/覆盖率提示 UI 尚未批准。

**计算（已确认方向）**：`COUNT(DISTINCT 已明确报告 manual_intervention_count > 0 的 Run) / COUNT(DISTINCT 同筛选范围全部技术 Run)`；分母**包含介入字段未报告的 Run**，但这些 Run 的字段仍为未知，不作 0 值回填。单 Run 多次人工介入只记一个介入 Run；人工介入**事件次数**另行从已报告的次数求和，不能代替 Run 介入率分子。分母为零及字段全部未知时如何展示尚待确认。

**来源**：技术 Run 来自去重的 `(agent_id, source_run_id)`；有介入事实必须由调用侧真实观测上报。严格 Run v1 **不含** `manual_intervention_count`，v1.1 中的该字段仍仅为未批准草案；本决议并未授权修改现有协议或强制调用方提供该字段。

**未决标准**：人工介入事件的可计数定义（人工接管、必经审批、复核等），RUNNING/FAILED/CANCELLED 与 SUCCEEDED 的参与资格、统计日采用 started_at/finished_at、时区/窗口、介入字段必填/真零/迟报/格式异常、上报覆盖率口径/精度与空值、旧 v1、权限/环境/归档历史与审计全部继续待确认。**此方案只能反映已知介入占全部 Run 比例，不是采集完整的实际人工介入率。**

**B06 集团实时执行动态方案 A 已确认（2026-10-11）：真实授权技术 Run 为基础、有可信脱敏摘要时可选展示、缺摘要回退中性技术状态；最近 N、排序/RUNNING/去重/刷新/脱敏/权限审计等仍待确认。下一项 B07 集团节省工时月趋势待议，详见 [21 逐项确认台账](21-metrics-field-confirmation-register.md)。**

## B06 集团实时执行动态 · 方案 A 已确认（2026-10-11）

| 维度 | 已确认核心原则及仍待确认的实施细节 |
| --- | --- |
| **展示** | **首页从真实 Run 展示 Agent 登记显示名、技术状态与时间**；可选展示**来源真实且已脱敏的简短活动摘要**。若无安全摘要，仍展示中性技术 Run 描述，不丢弃整条执行记录；具体标题、日期格式、每页 N 条、缺失状态文案待议 |
| **计算/查询** | 以**授权可见的实际唯一 Agent Run** 为来源，不能拿 DemoTicker、模拟计数当生产事实；同 Run HTTP 重传不能冒充不同执行。列表 N、排序用 started_at/finished_at/received_at、RUNNING→终态是更新行还是增加状态事件、分页/刷新/延迟等尚未确认 |
| **来源** | Agent 登记资料 + Run v1 已有 status/started_at/finished_at（可选项按 v1 限制）及可选调用侧脱敏活动摘要；严格 v1 **没有 summary/operation_type**，v1.1 提供的候选字段仍是**未批准草案**，未来字段/校验/版本另议，不能就地加到严格 v1 |
| **标准** | 技术 SUCCEEDED ≠ 业务已完成，不能让摘要暗示业务已付款、审批通过或交易已生效（无可验证业务事实）。严禁直接展示 Prompt/Response、合同/单据、凭证、个人信息等敏感原文；摘要可信判断、长度、脱敏方式、无内容、权限范围、环境与审计均待确认；已取消的场景演示不得重建 |

**明确只确认方案 A 展示与来源方向**：不决定摘要字段必须上报，也不要求对接业务系统结果或通过新接口强制采集文字；不自动把 B06 已选规则应用于详情 C10 或监控 E08（这些指标另有未决标准）。**下一项 B07 月度节省工时趋势尚未选择**：当前 MVP 文档 [17](17-agent-log-dashboard-mvp.md) 建议用 Run 量趋势代替，不能默认真实小时数。

## 3. 标准 Run 摘要（建议，示例数据均为虚构）

```json
{
  "schema_version": "1.0",
  "agent_code": "agent-sample-01",
  "run_id": "run-sample-0001",
  "status": "SUCCEEDED",
  "started_at": "2026-10-10T08:02:00+08:00",
  "finished_at": "2026-10-10T08:02:03+08:00",
  "duration_ms": 3000,
  "input_tokens": null,
  "output_tokens": null,
  "error_code": null,
  "error_message": null
}
```

调用身份/令牌通过服务端到服务端 `Authorization: Bearer` 校验，且应绑定授权 `agent_code`/环境，不能信任请求体自报身份。**服务端字段统一使用 `source_run_id` 存储，请求入参统一使用 `run_id`**；两者的映射由接收层完成。终态需要 `finished_at`，`started_at` 全状态必填；详见 [18](18-agent-run-reporting-standard.md)。

## 4. 状态与时间

- `RUNNING → SUCCEEDED / FAILED / CANCELLED`。如果源只发终态，允许直接写入终态；旧的 RUNNING 重试数据不得把终态覆盖。
- `UNKNOWN` 可以表示来源状态无法映射，不可计为 SUCCEEDED。
- `started_at`/ `finished_at` 源时间有时缺失，服务器写入 `received_at`，不可擅自当成真实完成时间。各 KPI 统一展示所用时间基准。
- 统计区域默认 `Asia/Shanghai`，时间窗半开 `[start, end)`，API 显示 `as_of` 和数据覆盖/最新接收时间。
- 命名为“在线”要求额外的健康协议；仅最近有一条 Run 只能称“最近活跃”。

## 5. 建议接口响应（虚构数据）

```json
{
  "as_of": "2026-10-10T08:30:00+08:00",
  "timezone": "Asia/Shanghai",
  "metric_scope": "AGENT_RUN",
  "metrics": {
    "registered_agents": {"value": 9, "quality": "DEMO"},
    "run_count": {"value": 663, "quality": "DEMO"},
    "run_success_rate": {"value": 0.972, "quality": "DEMO"},
    "avg_duration_ms": {"value": 4600, "quality": "DEMO"}
  },
  "latest_log_received_at": "2026-10-10T08:29:59+08:00"
}
```

生产 `quality` 不允许为 `DEMO`。未接入时可以给 `value=null, quality=UNAVAILABLE`，不能把示例 9 人/663 次填进去。

## 6. 数据质量验证

- 对相同筛选窗/部门，按 Agent 分组的 Run 数相加等于集团 Run 总数；
- `(agent_id, source_run_id)` 重复上报不能产生两条；
- `RUNNING` 不混入成功率分母；成功与失败统计时间口径一致；
- 没有耗时时 avg_duration_ms 为 null；
- 缺 Run 日志、数据延迟、真实 0 分开；
- 正式看板没有“核验节省工时”“已结算成本”“真实业务成功率”等未经源系统证实的项目。

扩展的业务 Task/Run/成本账本逻辑归档在 [14](14-employee-management.md)、[15](15-data-integration.md)，**非 MVP 要求**。

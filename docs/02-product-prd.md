# 02｜产品需求文档 PRD（讨论稿）

> 状态：**Draft，非已审批需求**。目标是把附件 v6 的看板转成真正可运营、可度量、可审计的集团数字员工平台。原型现有页面与建议新增能力分列。
>
> **已确认的两项约束**：集团管理层优先（2026-10-09）；先依据 [原始可交互 HTML](../prototype/index.html) **1:1 还原页面布局**（2026-10-10）。具体 [06 管理层驾驶舱建议](06-management-dashboard.md) 和 [07 技术架构取舍](07-executive-data-architecture.md) 是下一阶段的候选优化，不应覆盖首期 UI 基准；详细验收见 [08 UI 还原规范](08-ui-reproduction.md)。

## 1. 价值主张与边界

平台只负责**登记、观测、分析、告警治理与证据展示**；业务执行留在现有 Agent 平台和领域系统。数字员工不是大模型账号数量，不是工具调用数量，更不是虚拟人展示卡片。

**不做（MVP）**：Agent 编排引擎、统一对话入口、完整低代码工作流编辑器、自动付款、直接修改 ERP/POS 主数据、AI 模型训练、推翻既有任务审批系统。

**MVP 的最小闭环**：登记员工 → 接入两个真实业务场景的执行事件 → 产生可追踪业务任务 → 在看板展示可靠指标 → 异常进入处置流程 → 形成可核对的月度价值报告。

## 2. 角色与场景

**排序规则（首期已确认）**：集团管理者是主要受众；部门负责人是第二受众；信息中心运维是支撑受众。首页按经营叙事排版，技术详情留在监控中心。

| 角色 | 主要问题 | 核心操作 | 默认范围 |
| --- | --- | --- | --- |
| 集团管理者 | 投入产出和业务覆盖怎样 | 看汇总/趋势/排行、下钻证据 | 经授权的集团范围 |
| 部门负责人 | 本部门有没有产出，哪里卡住 | 认领员工、查看任务、分派待办、确认基线 | 本部门及授权业务域 |
| 员工产品负责人/场景 Owner | 我负责的流程是否稳定 | 查看任务质量、改进计划、处理异常 | 负责的员工/场景 |
| 平台运维 | 哪个步骤/依赖失败 | 搜索 trace、告警确认、重试建议与状态 | 授权技术范围 |
| 财务/审计 | 工时和成本可信么 | 查看口径版本、成本凭证与操作日志 | 授权财务审计范围 |
| 平台管理员 | 谁可以看、谁对指标负责 | 目录、接入密钥、规则配置、权限配置 | 最小必要范围 |

## 3. 导航与交互（先 1:1 还原原型，再评审增量优化）

**UI-F0 执行要求**：复刻原型的上下模块顺序、Topbar、导航、KPI、实时动态、员工目录、工时/成本图表以及监控和二级页面。下文 3.1 中任何“首屏重排、业务趋势上移、动态日志下移”等描述都属于 UI-F2 阶段建议，**不作为 UI-F0 的验收要求**。

### 3.1 运营总览（P0）

**顶部统一筛选器**：首屏露出统计周期（建议本月至今）、部门、业务场景；来源系统与数据质量作为高级筛选项，仍由后端强制授权。所有图表必须使用同一筛选上下文。

**核心卡片（建议排序，待最终评审）：**
- 主卡①已核验上线数字员工数；规划/未接入、接入失联分别显示。
- 主卡②完成**独立业务任务**数（业务回执），运行尝试和工具调用仅在下钻显示。
- 主卡③已核验释放工时；若无人工基线审定，必须显示“待核验”。
- 主卡④总运行成本；分已结算/估算，范围与分摊规则明示。
- 质量副栏：**业务成功率、重大异常与数据覆盖**，把技术监控从首屏主视觉移出。

**中区**：真实价值趋势（任务/工时/成本切换）+ 部门/场景贡献（显示覆盖与可信度）。

**下区**：部门员工目录（搜索/状态/归属/负责人）+ 重大风险与数据新鲜度摘要。原型“今日实时动态”移至监控中心；不同场景的工作量不可硬排序为同质生产力。

### 3.2 员工详情（二级，P0）

显示：员工 ID、业务名称、责任部门、建设部门、Owner、业务任务定义、版本与来源、运行/接入状态、最近心跳、上线审批证据。

四个 Tab/分区：
1. **概况与效能**：任务完成率/一次自动完成率/耗时 P50/P95/人工介入/成本/工时及口径。
2. **运行任务**：按业务 `task_id` 可查，打开执行尝试、步骤、错误、业务回执、人工节点。
3. **流程文档**：流程图/版本、业务 SOP、安全审批节点、监控负责人。原型“上传 1 张”可保留为单张主流程图，但后台需版本化。
4. **变更与审计**：员工版本、接入状态、度量配置和权限变更记录（MVP 只读）。

### 3.3 监控中心（P0 最小摘要，P1 扩展技术深度）

- 今日失败、超时、待人审、异常恢复、告警数量分开显示；附事件采集延迟。
- 告警列表支持：严重度、场景、责任人、指派、状态、最后变化时间、处理链接。
- 操作状态机：`OPEN → ACKNOWLEDGED → IN_PROGRESS → RESOLVED`；允许 `SUPPRESSED` 且必须填原因及失效时间。
- 每条告警关联 `task_id/run_id/trace_id`，有可见的事件时间线。MVP 可以同步已有工单系统，不新建复杂 ITSM。
- “重试”默认跳转至**原业务系统**，看板不得静默代执行有副作用的操作。

### 3.4 业务案例展示（二级，P0 内容 + P1 动态）

每个场景放：解决的人工问题、输入、关键步骤、人审点、输出、业务 Owner、运行接入状态、典型业务回执、工时估算方法、风险边界。**不展示敏感真实账单/收款账户等信息**。

## 4. 五个标杆场景的“完成事件”建议

| 场景 | 任务单位（建议） | 成功定义 / 结果证据 | 人工节点 | 先接什么数据 |
| --- | --- | --- | --- | --- |
| 智能报销 | 一份待处理物业账单/费用提单请求，拆单时有父子任务关系 | 原系统受理提单并返回业务单号；后续审核/付款作为独立阶段，不能提前冒充完成 | 匹配失败、预算/合同异常、员工确认与财务审核 | 提单请求 ID、阶段状态、回执、耗时、人工接管 |
| 菜品调整 | 一次经过确认的菜品变更请求（含门店范围/时间） | 菜品服务写入成功**且必要的生效/分发回执到位**；仅 Agent 回复“成功”不算 | 大范围/高风险变更需原系统确认审批 | 变更请求 ID、影响范围、校验/审批/生效事件 |
| 采购情报 | 一次明确的查询或一份报告交付；区分两种任务类型 | 结果交付到目标渠道或被业务方确认可用；可补充抽检质量 | 来源失效、低置信度、关键数据冲突 | 查询/报告 ID、交付状态、数据更新时间、人工抽检 |
| 门店巡检 | 一次门店-周期-巡检计划执行；异常整改另设工单 | 应检指标完成采集与校验；告警整改关闭是另一 SLA | 异常派单、复核关闭 | 巡检计划 ID、门店 ID（脱敏）、覆盖率、告警/闭环 |
| 稽查排班 | 一个排班周期的生成与发布工作单 | 排班表通过负责人复核并**发布**；算法求解成功不等于业务成功 | 排班负责人复核 | 排班批次 ID、约束冲突、版本、审批与发布状态 |

备注：上述完成定义是**建议口径**，必须由业务 Owner 签署；原型只提供流程线索。

## 5. 状态模型与数据质量

**生命周期**：`CANDIDATE → INTEGRATING → ACTIVE → PAUSED → RETIRED`。

**接入状态（独立）**：`NOT_CONNECTED / VERIFYING / CONNECTED / STALE / ERROR`。ACTIVE 但 STALE 不能显示为“正常在线”。

**数据可信度**：`DEMO / ESTIMATED / VERIFIED`。全局提供“只看验证数据”，DEMO 数据只能出现于明确演示模式，且演示模式不写入生产聚合。

**空状态**：尚未有数据、发生采集异常、指标不可计算必须不同显示；展示上次成功同步时间。

## 6. 非功能要求（第一版建议 SLO，待定稿）

- 数据时效：常规执行事件到看板目标 **≤ 60 秒 P95**（可在采集频率/源系统约束下调整）；趋势聚合最迟 T+1 校准。
- API：日常查询 P95 **≤ 1 秒**（具体体量待测）；分页与导出异步处理。
- 可用性：看板故障**不能阻断任何核心业务流程**；接入方上报失败可缓存重试或发送队列。
- 可追踪：事件接入幂等；关键写操作100%审计；按源系统标注采集缺口。
- 合规：敏感字段默认脱敏；源业务 ID 不直接对公开链接暴露；多部门访问最小授权。
- 范围：优先覆盖两个端到端业务场景，其余场景接入后逐步扩大并回归验证。

## 7. 交互验收样例

1. 对比相同时间窗下首页“任务完成数”与员工详情之和（数据范围相同）：应严格一致。
2. 同一任务失败重试 3 次后成功：**任务总量 1、Run 数 3、最终业务成功 1**。
3. 人工审核中：不计为最终成功；进入待确认队列，计人工介入，但不自动算失败。
4. 采集停滞：显示“数据延迟/不可用”和告警，不继续伪造实时数字。
5. 一名被标为“运行中”的员工无接入验证：标记“未核验”，不并入已验证上线数。
6. 未授权部门进入员工详情：返回权限错误，导出也不能越权。
7. 告警标为“忽略”：必须有操作者、原因和有效期，能追溯。

# 19｜原型全量指标与数据覆盖审计：Run 上报 v1 的差距

> **状态：原型审阅结论（2026-10-10），不是上报 v1.1 已批准的修改。** 项目发起人指出仅 Run 状态/耗时/Token 不能覆盖原始看板，要求先完整检查原型指标；本文件逐页对照 `prototype/index.html`、内联 `emps`、`perfData`、`genTrend`、`pushFeed` 与 ECharts 配置。**此次不修改[18 已写入的 v1 上报协议](18-agent-run-reporting-standard.md)。**
>
> 原型基线 Blob：`92d6df5d024a665cb88fcff9724fcb8ac1787225`。完整原型：[HTML](../prototype/index.html)。MVP 已确认只做 Agent 登记、调用处采集 Agent 日志、展示看板；这里不主张额外开发业务系统回执/财务治理平台。

## 1. 总览 p0：所有真实可见指标

原型 HTML 行 183—223；员工数据/图表与脚本在行 642—705、735—752，实时逻辑在 925—1024。

| 可见项 | 示例或意义 | 原型内数据如何产生 | 仅上报 v1 能否供给 | 缺少什么 |
| --- | --- | --- | --- | --- |
| 数字员工总数 | 9 | `emps.length` | **能** | Agent 登记 |
| 真实在用数 | 5 | `emps.real === true` | **不能仅靠 Run** | Agent 注册记录内的接入/使用状态；不等于 enabled / 最近日志 |
| 当日执行任务 | 663 | `today=663`，`pushFeed` 模拟增加；各员工 `perfData.today` 合计 663 | **部分** | Run 可算执行次数，**不能证明是业务任务**；改标签为“Agent Run” |
| 当日成本、单均成本 | ¥308、¥0.46 | 各员工 `today × perfData.cost`，初始约 ¥308.2；再随机增加 | **不能** | 实际已计费金额/价格表和 usage，或清晰标注估算且有依据 |
| 自动化成功率 | 96.8% | 静态 HTML | **部分** | Run success 可代“技术执行成功率”，不是业务自动化完成 |
| 人工介入率 | 1.8% | 静态 HTML；`perfData.intervene` 每员工静态值，未被渲染绑定 | **不能** | Run 是否人工接管/复核，或独立统计（要定分母） |
| 目标 ≥95% | 固定阈值 | HTML 静态文字 | **不能从 Run 推导** | 配置阈值/展示目标，属于管理配置 |
| 实时执行动态 | 最近若干次动作 | `evPool` 固定文本；每 6s 模拟生成 | **部分** | Run 时间/状态有，但缺安全的操作标题/任务摘要 |
| 九员工部门分组 | 信息/财务/采购/内审/运营 | `emps` 静态元数据 | **能，来自登记** | Agent 部门、名称、负责人等 |
| 节省工时趋势 | 1—9 月小时数 | `c-hours` **静态**数组 `[290,387,484,629,726,774,629,484,436]` | **不能** | 工时基线或每次任务估算，不能由 Run 耗时自动产生 |
| 成本趋势 | 1—9 月 RMB | `genTrend(累计执行次数) × perfData.cost` 聚合 | **不能** | 真实费用上报或 usage×价格配置（必须标估算） |
| 场景效能排行 | 节省工时 Top 8 | `c-top` 静态小时数 `[1120,780,640,620,540,380,320,260]` | **不能** | 工时指标；若仅 Run 数据，只能改成执行量/成功率排行 |

**员工卡**（HTML 动态生成行 654—681）：每个员工展示 `name, group, dept, stat, badge, runs, ok, hrs, ver, src, created, owner`，其中累计执行/成功率/节省工时三项是展示数值，其余属于注册/管理元数据。五人有“真实在用”和场景演示按钮。**注意**：原型九人全写为“运行中”，但其中四人并未标为真实在用；不能把页面状态当连接健康探测。

## 2. 详情 p11：4 KPI + 3 图 + 元数据 + 执行动态

原型 HTML 行 225—276；渲染行 754—795、991—1019。

| 区域 | 原型可见内容 | 仅靠 v1 可否 | 来源需求 |
| --- | --- | --- | --- |
| 头部身份 | 名称、部门、运行状态、版本、是否真实在用 | **登记** | Agent 元数据与接入标记 |
| 累计执行 | 累计次数 | **能** | 唯一 Run 计数（与任务语义区分） |
| 自动化成功率 | 一次通过率 | **部分** | v1 成功/失败仅可计算“Run 技术成功率”；真正一次通过需明确重试/人工定义 |
| 累计节省工时 | 小时 | **不能** | 经说明的人工基线/估算来源 |
| 今日执行 | 次数 | **能** | Run + started_at |
| 最近执行 | 时间戳 | **能** | 最近 Run 的 started/finished_at，区分收到时间 |
| 月度执行趋势 | 柱图，次数/月 | **能** | 按月份汇总真实 Run |
| 月度节省工时 | 面积折线，小时/月 | **不能** | 估算或事实来源 |
| 月度成本 | 柱图，元/月 | **不能** | 实际费用或有依据的估算 |
| 工作流 | 本地上传预览一张 PDF/图片 | **不属于 Run** | UI-F0 演示可保留；正式持久化需单独文件存储，MVP 可暂不做 |
| 最近执行记录 | 当前员工执行动作文本和时间 | **部分** | 缺 `summary/operation` 等脱敏展示字段 |

`perfData` 每员工有 `today, cost, intervene, score, grade`，**被展示/使用的主要是 today 与 cost**（成本汇总/详情曲线）；`intervene, score, grade` 目前不被详情页面消费，不应擅自新增评分功能。

`genTrend(total)` 以固定权重 `[.06,.08,.10,.13,.15,.16,.13,.10,.09]` 将累计数拆成 9 个月，**不是按真实时间戳汇总**。UI-F1 应使用 Run 真实发生时间。

## 3. 五场景 p7：运行数与文字提出的业务指标不同

原型 HTML 行 279—552。

### 页面确实显示并动态变化的数据

| 场景 | 当前示例 | 展示标题 | 仅靠 v1 能否 |
| --- | --- | --- | --- |
| 智能报销 | 132 | 今日执行 + 最近执行时间 | 如果场景固定关联已登记 Agent，能算 Run 数；不等于提单数 |
| 菜品调整 | 86 | 今日执行 + 最近执行时间 | 同上；不等于变更生效数 |
| 采购情报 | 45 | 今日查询 + 最近执行时间 | **不能一概等同 Run**，需“查询”操作类型或明确该 Agent 单次调用只做一次查询 |
| 门店巡检 | 128 | 今日巡检 + 最近执行时间 | 需要“巡检”计量定义；一次 Run 可能检查多个门店 |
| 稽查排班 | 6 | 今日处理 + 最近执行时间 | 需要“处理”定义；原型说明包含生成、调整、查询多种动作 |

场景页 `rs-live` 是固定文本模板循环，每 6 秒更新计数和最近时间，与真实数据源无关。

### 仅写在“五个场景在平台上的生命周期位置”说明表内，**没有动态统计实现**的指标

- 智能报销：提单成功率 / 介入率 / 单均耗时；
- 菜品调整：调用量 / 成功率 / 变更审计；
- 采购情报：数据更新频率 / 查询量 / 报告数；
- 门店巡检：巡检覆盖率 / 异常闭环率；
- 稽查排班：规则命中率 / 排班调整率。

这些需要源业务量、分母/结果、审计数据或专项统计，不是自动从 Agent 的 `SUCCEEDED`、`FAILED` 推导的本期事实。可以保留**静态场景介绍**，或将其作为未来的**可选扩展指标**，但不能标成 MVP 已可计算。

## 4. 监控 p4：4 KPI + 告警 + 执行流水

原型 HTML 行 554—598，动态逻辑行 914—962。

| 内容 | 演示值 | v1 覆盖 | 尚缺 |
| --- | --- | --- | --- |
| 今日执行 | 663 | **能（Run）** | 明确是 Run 启动次数 |
| 执行成功率 | 96.8% | **能（技术口径）** | 标签改“技术成功率” |
| 人工介入 | 23、1.8% | **不能** | 人工介入标记/次数字段和时间口径 |
| 异常事件 | 17 | **部分** | FAILED Run 可作失败次数，但不等同独立异常事件 |
| 自动恢复 / 待处理 | 15 / 2 | **不能** | 告警事件、恢复关联、确认/忽略状态或外部运维系统来源 |
| 实时告警列表 | 5 条示例，含失败原因/重试/人工确认/处理按钮 | **部分** | 错误码/摘要可以生成“近期失败”；但不能推导待处理状态与恢复率 |
| 执行流水 | 时间、员工、任务、结果、耗时 | **部分** | v1 有时间/状态/时长，缺脱敏执行内容 `summary` |

原型标题声称“最近 10 条”，但 HTML 初始表实际有 **12 条**，动态更新也限制为 12；这是演示口径/文案不一致，而不是新产品必须保留的业务约束。

## 5. 从原型源码直接发现的演示数据问题

1. `emps` 有 **9 个条目，累计执行数相加为 34,000**；`real:true` 仅 5 个。原型九张员工卡数据是硬编码，不能直接当作真实登记资产。
2. `perfData.today` **9 人相加恰好 663**；当日成本由九人“当日执行 × 固定单均成本”计算约 **¥308.2**，页面展示 **¥308**；后续 `pushFeed` 使用随机量持续增加成本。这既非真实 Token 计费，也非财务对账。
3. 九张员工卡的节省工时数相加为 **4,840h**；首页月度节省工时固定数组相加为 **4,839h**。这 1h 差异说明两处只是演示数据，不能用来要求生产系统照样对账。
4. 页面上“人工介入 **23** 次、介入率 **1.8%**”与同页“今日执行 **663** 次”若以 Run 数做分母会得 **约 3.47%**，不能同时按同一时间窗/分母解释。实际成功率与介入率基数必须统一定义。
5. 异常事件卡写 **17**（15 自动恢复 + 2 待处理），但可见 5 个示例告警中**3 条待处理、2 条已恢复/完成**；不能以这些示例反推真实告警总量。
6. 顶栏 `#clock` 初始是 `--:--:--`，源码脚本没有看到更新这个元素的逻辑；“系统运行中”是静态文字，不是独立运行健康监测。
7. `perfData.intervene/score/grade` 存在于模拟 JS，但没有实现相应的真实绩效展示。不能默认这些指标已经能算或已经有页面。
8. 原型的执行流水与动态 Feed 文本由固定 `evPool` 和模板生成，输出可能带“已受理/已调整/已完成”等业务叙述，但不是源系统已证明的结果。

## 6. v1 上报字段覆盖缺口：按优先级补什么

**目前 v1**：`schema_version, agent_code, run_id, status, started_at, finished_at?, duration_ms?, input_tokens?, output_tokens?, error_code?, error_message?, trace_id?`。

| 数据字段/来源 | 目的 | 如何最低成本取得 | 建议 |
| --- | --- | --- | --- |
| `agent_code` → Agent 注册表 | 名称、部门、Owner、来源、版本、创建时间、场景映射 | 已有登记 CRUD | **P0，无须放到每条 Run** |
| `summary` / `operation_type` | 实时动态中的“做了什么”；查询/报告/巡检的操作分组 | 调用边界提供**脱敏、安全的简短活动摘要**和枚举 | **建议上报 v1.1 优先考虑** |
| `manual_intervention` 或 `intervention_count` | 人工介入次数/介入率 | 调用方**确实知道**发生了人工接管时填；未提供为 null | **建议 v1.1 可选，单/多次口径要先确定** |
| `cost_amount` + `currency` + `cost_quality` | 当日/各月实际或估算成本 | 来源平台真实账单 / 调用侧真实计费；Token×可审计定价版本也可算“估算” | **建议可选，不得无依据算值** |
| 工时基线（配置）/ `estimated_saved_minutes` + basis | 工时趋势、效能排行 | 先由业务 Owner 给**人工基线/估算规则**，再计算并标“估算” | **用户若坚持保留该指标再纳入；不能直接从 Run 耗时推导** |
| retry / recovery correlation | 异常恢复、重试表现 | 同一业务动作多个独立 Run 需一个关联 ID；或明确调用内部重试次数 | **P1；先做最近失败列表更简单** |
| 告警状态及处置记录 | 自动恢复/待处理/处理/忽略 | 独立告警事实与状态，不是简单 Run status | **非当前三功能 MVP，除非重新确认** |
| 场景特有计量 | 巡检覆盖、报告数、排班命中等 | 需明确数量分子/分母、操作类型与源业务统计 | **先展示静态介绍，不能伪造实时值** |
| 文件/工作流图 | 详情展示 | UI-F0 本地预览；正式持久化可用单文件附件服务 | **可选、不属于 Run 上报字段** |

推荐采取**两层结构**而不是把原型所有卡片内容塞进一个上报 JSON：
- **Agent 登记/配置数据**：ID、部门、负责人、版本、接入标志、场景说明和可选人工基线；
- **Run 执行上报数据**：唯一执行、状态、时间、错误、用量，按需扩展脱敏摘要/操作类型/人工介入/成本；
- **从 Run 聚合**：运行量、成功率、平均耗时、趋势、排行和最近活动；
- **无法从 Run 确定的事实**：节省工时、真实业务交付、告警恢复率、场景覆盖率必须显示“暂无依据/估算”或调整为技术指标。

这不会改变用户已明确的三项 MVP 功能，也不需要引入新的通用 Connector、业务 Task 账本和大数据平台。

## 7. 后续协议修订的最低验收目标（建议，而非本次已确认）

1. 登记字段覆盖员工卡的名称/部门/Owner/版本/场景等信息；
2. 每条 Run 可以安全展示“执行了什么”，而不是只有“Agent 成功/失败”；
3. 技术执行量、成功率、耗时、失败列表、所有真实可计算趋势基于唯一 Run 统计；
4. 人工介入、Token/成本、工时：**有真实来源才显示，有估算规则标估算，没有则显示不可用**；
5. 五场景可按 Agent 或明确 `operation_type` 过滤，**只把 Run 次数称为 Run 次数**；
6. 无法从 Run 推导的告警处置/专项业务指标不在 P0 假装完整支持；
7. 所有原型演示静态数据与正式 Provider 隔离；验收时用真实上报样本而不是靠固定数字。

**本审计结论**：现有 [18 上报 v1](18-agent-run-reporting-standard.md) 是最小 Run 状态契约，但**不是原型全指标采集协议**。需要先确定哪些原型指标必须保留原名称、允许估算或在正式环境替换为 Agent 技术指标，然后再审议 v1.1 可选字段。**不应先改接口再找数据依据。**
